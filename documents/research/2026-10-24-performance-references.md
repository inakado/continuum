# Производительность: первичные референсы для Continuum

Дата проверки источников: 24.10.2026. Исследование, не реализация и не результат нагрузочного теста нашего сайта. Контекст: Next.js 16.4 / React 19, NestJS / Prisma 7 / PostgreSQL 16, TanStack Query. Реальный рабочий набор — до 30 учеников **в одном классе** и до 30 заданий в работе; классов и накопленных работ во всей базе может быть больше. Источники ниже не задают автоматического порога «после N записей обязательно Redis».

## Семь практик и границы переноса

Предложенный здесь разовый запуск впоследствии выполнен; результат, исправления и актуальные ограничения — в [отчёте React Doctor/профиля](2026-10-25-react-performance.md). Этот документ сохраняет исходное исследование источников на указанную дату.

| Практика | Что подтверждено первичным источником | Вывод для нашего масштаба, не готовая реализация |
|---|---|---|
| Измерять конкретное взаимодействие | React Profiler даёт время commit/render; стандартная production-сборка отключает profiling из-за его накладных расходов. React советует измерять дорогие вычисления на production-подобной сборке. [Profiler](https://react.dev/reference/react/Profiler), [useMemo](https://react.dev/reference/react/useMemo) | Измерить ввод ответа, переключение задачи, открытие формул и отчёта. Основной набор 30×30; дополнительный — три класса 90×30. Не измерять только пустую страницу или dev-mode. Это предложение сценариев, не обещание полученных timings. |
| Выбирать только нужные поля и избегать N+1 | Prisma по умолчанию возвращает все scalar fields. В официальных best practices показаны `select`, nested read и пакетный `in` вместо SQL в цикле. [Select fields, v7](https://www.prisma.io/docs/orm/v7/prisma-client/queries/select-fields), [исходник best practices v7](https://github.com/prisma/web/blob/main/apps/docs/content/docs/orm/v7/more/best-practices.mdx) | Сначала убрать реально избыточный JSON/условия из summary-запросов и подтвердить число SQL. Не раздроблять запросы на отдельное чтение каждого ученика. При 30×30 чтение одного отчёта целиком само по себе не доказывает проблему. |
| Ограничивать растущие каталоги, не дробить малый связный отчёт автоматически | Prisma допускает offset для небольших наборов и нумерованных страниц; cursor полезнее для глубокого последовательного просмотра. Реальный продукт Documenso документирует список с `page`/`perPage`, отдельное получение документа и максимальный размер страницы. [Prisma pagination](https://www.prisma.io/docs/orm/v7/prisma-client/queries/pagination), [Documenso API source](https://github.com/documenso/documenso/blob/main/apps/docs/content/docs/developers/api/documents.mdx) | Общий банк/история работ/все ученики могут расти независимо от размера класса. Их имеет смысл ограничивать по фактическому объёму. Не переносить автоматически размер страницы Documenso и не разбивать 30 строк матрицы на несколько сетевых запросов без измерения. |
| Настраивать фоновые запросы по сценарию | В TanStack `refetchInterval` независим от `staleTime`; structural sharing сохраняет неизменившиеся ссылки. Подписка на используемые properties и `select` уже ограничивают перерисовки. [Defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [Render optimizations](https://tanstack.com/query/latest/docs/framework/react/guides/render-optimizations) | Посчитать запросы при открытом/скрытом экране, не менять число 15 секунд на 60 вслепую. Не выключать контроль отзыва работ, прав и истечения сессии ради красивой метрики. Не дублировать встроенный query-cache собственным слоем. |
| Профилировать bundle и откладывать действительно тяжёлые модули | Next даёт Turbopack analyzer и lazy loading client-компонентов/библиотек. Analyzer встроен с 16.1; export сохранённого графа появился в 16.4. [Bundle analysis](https://nextjs.org/docs/app/guides/package-bundling), [Lazy loading](https://nextjs.org/docs/app/guides/lazy-loading) | В установленном локальном Next 16.4.1 `next/dist/bin/next` присутствуют `analyze`, `--output` и `analyze export`: новая npm-зависимость для первичного анализа не обязательна. Проверить, какие PDF/MathJax/редакторские модули реально входят в initial route, а не судить по наличию пакета в package.json. |
| Проверять передачу данных и сжатие на существующем proxy | Nest рекомендует переносить compression на reverse proxy для production; сжатие уменьшает response body. [Nest compression](https://docs.nestjs.com/techniques/compression) | Сравнить фактический `Content-Encoding` и байты HTML/JS/JSON. Если JSON не сжимается и заметно велик — рассмотреть существующий Nginx. Повторно сжимать PDF/JPEG/WebP обычно бессмысленно; не ставить новый middleware, пока proxy уже справляется. |
| Индексы и memo — после причины, не ради числа рекомендаций | PostgreSQL `EXPLAIN` показывает план; `ANALYZE` действительно выполняет запрос и добавляет измерительную стоимость. React `memo` — оптимизация, не гарантия; меняющиеся props/context ограничивают её эффект. [PostgreSQL 16 EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html), [React memo](https://react.dev/reference/react/memo) | Проверить медленный read SQL на изолированной базе, затем нужный индекс; не добавлять индексы всем полям. Memo рассматривать для подтверждённо дорогого Markdown/формул или строк таблицы. 900 ячеек сами по себе не основание виртуализировать интерфейс. |

## React Doctor: что это даёт и куда обращается

Официальный проект — [millionco/react-doctor](https://github.com/millionco/react-doctor), CLI — статический анализатор правил; его health score не является замером задержки нашего API или времени ответа на ввод. Есть отдельный runtime `scan`, который открывает изолированный Chrome-профиль и пишет локальный trace; trace может содержать URLs/пути и сведения о React. [CLI reference](https://www.react.doctor/docs/reference/cli-reference).

### Документированные сетевые функции

- CLI telemetry: Sentry получает crash-данные, Axiom — traces/usage через OTLP; при явной настройке используется свой OTLP collector. CLI reference документирует отключение score/crash reporting и отдельно Socket; наличие CLI не означает отсутствия сетевых функций. Официальная data-use страница описывает другой сценарий — GitHub App с выгрузкой архива кода в Vercel Sandbox. [CLI reference](https://www.react.doctor/docs/reference/cli-reference), [Data use](https://www.react.doctor/docs/legal/data-use).
- Есть отдельные score API и проверка зависимостей через Socket.dev. Поэтому утверждение «только локальный CLI, значит сети нет» неверно. [CLI options](https://www.react.doctor/docs/reference/cli-reference).

### Что проверено именно в исходниках

Ревизия публичного main: `84ad0c8d0df7a3ab7d26946367fae3bc39c100d0`. Скачаны только отдельные исходники во временный каталог; ничего не устанавливалось и не запускалось.

- [`is-telemetry-enabled.ts`](https://github.com/millionco/react-doctor/blob/84ad0c8d0df7a3ab7d26946367fae3bc39c100d0/packages/react-doctor/src/cli/utils/is-telemetry-enabled.ts) отключает telemetry при `--no-score`, `--no-telemetry` или `REACT_DOCTOR_NO_TELEMETRY`. Это решение читается до разбора CLI.
- [`cli/index.ts`](https://github.com/millionco/react-doctor/blob/84ad0c8d0df7a3ab7d26946367fae3bc39c100d0/packages/react-doctor/src/cli/index.ts) объявляет `--no-telemetry` alias для `--no-score`, отдельный `--no-supply-chain`, `--json`, `--project`, `--scope`, `--max-duration`, `--blocking none`. `install` и `ci install` — отдельные команды с записью skill/hooks/workflow, не нужные для разового сканирования.
- [`request-score.ts`](https://github.com/millionco/react-doctor/blob/84ad0c8d0df7a3ab7d26946367fae3bc39c100d0/packages/core/src/request-score.ts) отправляет gzip POST с diagnostics: `fileContext`, `fixGroupId`, `contextRanges` исключаются, путь скраббится; остальные diagnostic-поля остаются. Metadata может включать repo/SHA/framework и CI-поля. Это отдельный канал от описанной telemetry, поэтому общее обещание «всё остаётся локально» без выключателей неточно.
- [`check-supply-chain.ts`](https://github.com/millionco/react-doctor/blob/84ad0c8d0df7a3ab7d26946367fae3bc39c100d0/packages/core/src/check-supply-chain.ts) делает запрос на `firewall-api.socket.dev/purl/<encoded-purl>` для зависимости; кеш не исключает сетевой вызов при miss. `--no-score` не равен отключению Socket.

### Предложение для отдельного будущего запуска

Разовый advisory scan только `apps/web`, с проверенной pinned-версией, `--no-telemetry` (также выключает score), `--no-supply-chain`, ограничением времени, JSON локально и `--blocking none`. Ничего не исправлять автоматически ради 100/100; вывод сверять с нашим codebase и реальным профилем. CLI не нужен в runtime и пока не нужен новый обязательный CI gate.

Документированного единого `--offline` в проверенном CLI reference не обнаружено. Отключение перечисленных функций не является доказательством полного отсутствия сети у всего dependency graph/config/plugins; для строгой гарантии нужен запуск в окружении с запрещённым исходящим трафиком после отдельной подготовки пакета. Здесь такой запуск не выполнялся.

## Что сейчас не обосновано

Это вывод для согласованного масштаба и текущей стадии исследования, не универсальное правило: миграция Express→Fastify, Redis, WebSocket, отдельный worker, материализация статистики, разбиение каждого задания на отдельный API request, глобальные memo и виртуализация таблицы пока не имеют доказанной пользы. Официальный Nest поддерживает более быстрый HTTP adapter, но предупреждает о несовместимости Express-specific recipes; синтетический framework benchmark не показывает причину задержки конкретного приложения. [Nest performance](https://docs.nestjs.com/techniques/performance).

Первые кандидаты следует выбирать из фактических замеров нашего проекта. Этот файл даёт первичные основания и границы переноса, а не подтверждает найденный у нас bottleneck.
