# Доступ локального проверяющего с двух компьютеров

Дата исследования: 2026-10-18. Статус: исследование для Э6, не работающий контракт. Только первичные источники; продуктовые рекомендации ниже — вывод для Continuum, не требования внешних стандартов. После обсуждения пользователь выбрал доверенный локальный агент без подтверждения пачек на сайте; актуальное решение — в [контракте Э6](../exec-plans/active/2026-10-18-reviewer-api-contract.md).

## Что делают существующие решения

| Подход | Подтверждённое поведение | Вывод для проекта |
| --- | --- | --- |
| Именованный ограниченный токен | GitHub fine-grained PAT ограничивается владельцем ресурсов, выбранными репозиториями и разрешениями; задаётся срок действия. [GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) | Аналог для v1: отдельный ключ каждого устройства, права и доступные назначения; не общий пароль преподавателя. |

[GitHub CLI](https://cli.github.com/manual/gh_auth_login) | CLI скрывает секрет от обычного рабочего процесса. Для нашего клиента plaintext fallback лучше запретить. |
| OAuth Authorization Code + PKCE | Native app использует внешний браузер, public client обязан использовать PKCE. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) | Хорошая следующая версия входа без копирования ключа, но нужны authorization server, redirects, token lifecycle; для двух управляемых установок необязательна. |
| OAuth Device Authorization | Устройство показывает URI/код и опрашивает token endpoint; RFC не предлагает заменять этим браузерный OAuth на способных устройствах. [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628) | Подходит headless/удалённому CLI без удобного callback, не нужен только потому, что компьютеров два. |
| MCP | HTTP authorization опирается на OAuth, PKCE и discovery; stdio использует иной путь получения credentials. Token passthrough без проверки предназначения запрещён. [Спецификация](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [безопасность](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) | MCP — адаптер инструментов, не замена доменных прав. Начать с REST + CLI; при необходимости добавить локальный stdio-адаптер над тем же клиентом. |
| Специальный Agent Auth | Better Auth предлагает регистрацию агентов, approval и короткоживущие capability JWT, адаптеры OpenAPI/MCP; прямо предупреждает о нестабильности стандарта. [Agent Auth](https://better-auth.com/docs/plugins/agent-auth) | Не делать экспериментальный agent protocol обязательной зависимостью Э6. |

## Better Auth: применимость к pinned версии

Локально в `apps/api/package.json` закреплён `better-auth@1.6.23`; `@better-auth/api-key` в package/lock пока отсутствует. Текущий сайт документации показывает более новую версию. Однако официальный tag `v1.6.23` уже содержит отдельный пакет [`@better-auth/api-key@1.6.23`](https://raw.githubusercontent.com/better-auth/better-auth/v1.6.23/packages/api-key/package.json).

В [types.ts этого tag](https://raw.githubusercontent.com/better-auth/better-auth/v1.6.23/packages/api-key/src/types.ts) есть `permissions`, `keyExpiration`, `rateLimit`, `enabled`, `expiresAt`; hashing включён, `enableSessionForAPIKeys` выключен по умолчанию. Рекомендуется явно сохранить `disableKeyHashing: false`, `enableSessionForAPIKeys: false`, database storage. Обычные session routes не должны принимать reviewer key как вход преподавателя.

Плагин проверяет ключ и разрешения, но не знает владение нашими назначениями. Guard должен отдельно проверить principal, отзыв делегирования, разрешённый assignment и нужное действие. [Verify API](https://better-auth.com/docs/plugins/api-key), [опции](https://better-auth.com/docs/plugins/api-key/reference).

Сырой ключ возвращается при создании; управление включает отключение и удаление. В [create-api-key.ts версии1.6.23](https://raw.githubusercontent.com/better-auth/better-auth/v1.6.23/packages/api-key/src/routes/create-api-key.ts) HTTP-клиент не может задавать server-only `permissions`, rate limits и произвольный `userId`. Нужен наш session-protected endpoint выдачи с серверной политикой, а не прямое принятие желаемых scope из браузера.

Перед реализацией проверить совместимость отдельного пакета, Prisma schema и Nest adapter; public endpoints плагина не должны позволять обходить ограничивающий broker. Особенно проверить TTL тестом с часами: request `expiresIn` описан в секундах, комментарий `defaultExpiresIn` в tagged types упоминает миллисекунды. Не копировать числовые значения из разных API без проверки runtime.

## Рекомендуемый минимальный v1

1. Разделить человека, устройство и доступ. У коллеги собственная учётная запись/идентичность и явное делегирование выбранных назначений; не выдавать ему токен владельца. У каждого компьютера отдельный именованный ключ. «Per-device» здесь означает отдельную управляемую запись, не криптографическую привязку к железу: украденный bearer key можно скопировать.
2. Разделить права `read`, `draft:write`, `publish`, но не требовать разные ключи для каждого действия: ключ владельца может разрешать полный цикл, а публикация коллегой чужих работ требует явного grant. Ограничение ресурсов хранить в доменном grant, не только в редактируемой metadata ключа. Отозванный grant, отключённый principal или истёкший ключ прекращают следующие запросы. Устройства не требуют входящих соединений, SSH или доступа к БД/S3: только исходящий HTTPS в наш API.
3. Предлагаемый TTL основного ключа —30 дней с ручным перевыпуском. Секрет вводится человеком один раз скрытым prompt, хранится в macOS Keychain, не в Git, `.env`, чате, shell history или выводе агента. CLI читает его сам и не печатает headers. Рецензии/фото — чувствительные локальные файлы вне Git; секреты не передаются модели. Агент с произвольным shell остаётся доверенным процессом, Keychain не изолирует секрет от полностью скомпрометированного пользователя ОС.
4. Для обоих компьютеров — одинаковая CLI и конфигурация API origin, разные credentials. Журналировать `actorUserId`, `keyId`, grant, действие, IDs/revisions и `requestId`, но не ключи и содержимое фото. Совместное редактирование защищать `expectedRevision`, повтор операций — идемпотентностью, а не «последняя запись победила».
5. Фото отдавать авторизованным бинарным GET через reviewer API с повторной проверкой прав и `Cache-Control: no-store`; не раскрывать S3 credentials или вечные публичные URL. Малый v1 не нуждается в bearer URL. Если позже появятся presigned URL, их короткий срок не отменяет утечку и невозможность немедленно отозвать уже выданную ссылку.
6. Публиковать точный manifest: IDs рецензий, их ревизии и ревизии фото; сервер валидирует и фиксирует его атомарно. Команда не означает «всё накопившееся к этому моменту». Команда человека «проверь и загрузи» по уточнению пользователя разрешает полный цикл; обязательного второго подтверждения нет. Ключ без publish scope не может опубликовать; обладатель ключа с этим scope может вызвать API, и сервер не отличит человеческую команду от самостоятельного вызова. Пользователь принял доверенную локальную модель без независимого server-side approval; это осознанная граница, не свойство API key или MCP.

Не нужны серверная нейросеть, очередь AI-проверки, открытый локальный сервер, общая папка двух компьютеров или новый identity provider ради первого выпуска. Следующий рост — OAuth+PKCE для удобного подключения множества установок поверх неизменной модели прав; MCP при реальной необходимости интеграции хостов.
