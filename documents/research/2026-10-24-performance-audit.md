Первичные рекомендации и сравнение инструментов — в [отдельном исследовании источников](2026-10-24-performance-references.md); оставшиеся действия — [PERF-01](../exec-plans/deferred-roadmap.md#perf-01-измеримая-оптимизация-загрузки-данных).

## Масштаб и главный вывод

Это исходная линия до изменений. Последующие реализация и сравнение «до/после» завершены локально: [поиск/CSS/gzip](../exec-plans/completed/2026-10-24-small-performance-improvements.md), [React Doctor и профиль фронтенда](2026-10-25-react-performance.md). Формулировки «не запускался» и «ещё не реализованы» ниже описывают состояние именно на момент этого аудита, а не текущий backlog.

До 30 учеников **в одном классе**, до 30 заданий в работе. Классов, преподавателей, задач банка и накопленных работ во всей системе может быть больше. 30×30 и 90×30 — сценарии измерения одной работы для одного и трёх классов, а не ограничения продукта.

В проверенных локальных сценариях расчёт статистики и чтение работы не оказались тяжёлыми. Есть три более ограниченных кандидата: сократить запросы поиска банка, убрать неиспользуемый глобальный CSS редактора, проверить сжатие крупных JSON на существующем proxy. Это ещё не доказательство скорости браузера или пропускной способности production: HTTP, авторизация, сеть и отображение измерениями сервисов не покрыты.

## Что измерено

Локальный Docker: Node 24.18.0, linux/arm64, скомпилированные production-сервисы API и реальный PostgreSQL. Временный диагностический скрипт вызывал сервисы напрямую через Prisma, без HTTP и браузера. Для последовательных чтений — пять прогревов и 30 образцов; p95 — наблюдаемый перцентиль этих образцов, не нагрузочный SLA. Число SQL events включает команды управления транзакцией.

Созданы 210 временных учеников и три работы: 30×30, 90×30, 90×(25 тестовых + 5 развёрнутых). Для развёрнутых ответов использованы только синтетические записи фото/публикаций, файлы в S3 не загружались. После измерения все созданные ученики и работы удалены; очистка подтверждена скриптом. ### Что проверено на сервере

Read-only SSH: VPS имеет 2 vCPU и около 4 ГБ RAM. Нагрузочные или записывающие сценарии на production не запускались.

В `nginx -T` активен `gzip on`, расширенный `gzip_types` с `application/json` закомментирован. По умолчанию Nginx сжимает `text/html`. Публичный `/login` с `Accept-Encoding: gzip` действительно вернул `Content-Encoding: gzip`. В Nest bootstrap отдельного compression middleware нет. Таким образом, сжатие JSON не настроено существующим proxy; фактический заголовок и размер авторизованного production JSON в этом исследовании не измерялись. [Nginx gzip](https://nginx.org/en/docs/http/ngx_http_gzip_module.html).

## Что уже сделано рационально

- **Банк не выдаётся целиком.** `assessment-bank-read.service.ts` возвращает страницу из 50 summary-записей; выбранная задача, изображения и ключи читаются отдельно. Из БД для summary ещё читается полная `latestVersion`, а темы собираются по текущим версиям; на большом реальном банке эти два участка стоит измерить отдельно.
- **Ученик видит одну задачу.** `AssessmentQuestions.tsx` рендерит текущую, а не 30 длинных условий одновременно. Вся разрешённая работа приходит одним снимком, без ключей: при измеренных примерно 39 КБ JSON дробить её на 30 запросов пока не требуется.
- **Формулы уже защищены от лишней работы.** `AssessmentMarkdown.tsx` обёрнут в `memo`, MathJax загружается один раз при необходимости; эффект формулы зависит от её текста и display-режима. Новую глобальную мемоизацию без браузерного профиля добавлять не следует.
- **Статистика читает данные пакетно.** В `statistics-read.service.ts` число SQL events одинаково для 30 и 90 учеников; N+1 по ученикам в этих измерениях не обнаружен. Подробности ответов и файлов имеют отдельные чтения. В интерфейсе матрицы уже есть клиентские страницы по 20 строк.
- **Автосохранение последовательное.** Debounce 400 мс, очередь, `expectedRevision` и `requestId` защищают порядок и повтор. Оптимизация не должна обходить эти гарантии.
- **Фоновые опросы ограничены.** Выполнение и доступность — раз в 10 секунд, статистика — раз в 15 секунд, без polling в скрытой вкладке. Проверка доступности даёт около 3 запросов/с для 30 одновременно открытых работ и 9 запросов/с для 90, без учёта остальных запросов. Авторизация каждого HTTP-вызова сюда не измерена.
- **Основные списки не равны всем файлам.** Ученики выбираются через ограниченный `select`; PDF открывается по действию. Работы и назначения возвращают метаданные. При этом часть списков не имеет серверной пагинации, а ученический список сервером читает снимки назначенных версий: это может стать затратным с накоплением истории.

Эти выводы опираются на `apps/api/src/assessment-bank/assessment-bank-read.service.ts`, `apps/api/src/identity-access/identity-access-read.service.ts`, `apps/api/src/assessment-assignments/statistics-read.service.ts`, `statistics-aggregate.ts`, `apps/web/components/assessment/AssessmentQuestions.tsx`, `AssessmentMarkdown.tsx`, `apps/web/features/student-works/use-work-availability.ts` и соответствующие query hooks.

## Первые небольшие изменения

### 1. Сократить запросы поиска банка

`use-teacher-bank.ts` зависит от текущей строки напрямую; `TeacherBankScreen` и `WorkBankPicker` изменяют её при каждом символе. Query function не передаёт `AbortSignal`, хотя API client уже умеет его принимать. Поэтому быстрое слово может запустить несколько уже ненужных GET.

Предложение: ввод отображается сразу, серверный поиск — через примерно 300 мс паузы; устаревший GET отменяется через signal. Сохранить URL, возврат, выбранные задания и актуальные фильтры экспорта; отмену не показывать как ошибку. Не задерживать локальный поиск по уже полученной таблице. Приёмка — подсчёт запросов на быстрой строке и проверка медленного ответа, очистки, фильтров и Back.

### 2. Убрать неиспользуемый глобальный CSS Excalidraw

`apps/web/app/layout.tsx` импортирует `@excalidraw/excalidraw/index.css` для всех страниц и задаёт asset path. В действующих role-specific сценариях редактор не найден; hook темы не имеет рабочих потребителей. В сохранённой production-сборке CSS chunk с Excalidraw занимает 142 123 байта без сжатия, 22 158 байт при локальном gzip.

Предложение: убрать глобальное подключение неиспользуемого CSS и связанной инициализации, либо перенести в реально использующий редактор контур, если такой появится. Это уменьшает CSS для обеих ролей и login, но не означает, что на каждой странице сейчас скачивается JavaScript редактора: в проверенных initial chunks он не найден. Зависимость и все vendor-файлы удалять отдельным решением. Проверить обе роли, фокус, меню, формы и типографику.

### 3. Проверить сжатие больших read-only JSON в Nginx

Настроить на существующем proxy, затем сравнить bytes/headers и задержку того же авторизованного чтения до/после. Пример возможного выигрыша в синтетике: статистика 90×30 — около 151 КБ вместо 8 КБ gzip. Это потенциальное уменьшение передачи, не уже полученное ускорение production.

Сохранить `no-store` и права доступа. Не включать сжатие ответов с выдачей начальных паролей/ключей автоматически; не добавлять blanket cache приватного API. Сжатие PDF/JPEG и второй слой compression middleware не нужны. Nest рекомендует production compression на reverse proxy. [Nest compression](https://docs.nestjs.com/techniques/compression).

## Следующая очередь только после конкретного замера

**Фото.** `SolutionPhotoList.tsx` показывает уменьшенное изображение через `NextImage unoptimized`, но запрашивает оригинал; отдельной миниатюры нет. Большая фотография до 10 МиБ может стоить дороже всего JSON. Измерить реальные фото с телефона; если это заметная задержка — сделать закрытые миниатюры с сохранением ориентации, удалением вместе с ревизией и прежними правами. Это уже отдельное изменение upload/storage, а не обязательная мелкая правка прямо сейчас.

**Растущие общие списки.** Размер класса не ограничивает общую базу. Замер 231 ученика не показал дорогого чтения, но не покрывает годы истории. Вводить серверные поиск/страницы для реально тяжёлого каталога после измерения его JSON и SQL. Банк уже постраничный. Для небольшого связного отчёта 30/90×30 пока нет основания вводить отдельные серверные страницы матрицы, материализованные агрегаты или Redis. Это соответствует разграничению list/detail в реальном продукте [Documenso](https://github.com/documenso/documenso/blob/main/apps/docs/content/docs/developers/api/documents.mdx) и вариантам [Prisma pagination](https://www.prisma.io/docs/orm/v7/prisma-client/queries/pagination); чужой размер страницы не является нашим требованием.

**Повторные отчёты.** `refetchInterval` независим от `staleTime`, поэтому простое увеличение staleTime не прекращает polling. Пока стоимость мала, сохранить понятную актуализацию. Revision/ETag рассматривать, если повторы действительно расходуют заметное время/трафик. [TanStack defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

**Браузер.** Холодное открытие формул, переключение задач, ввод ответа, длинная матрица, реальные фото и слабое устройство ещё не профилировались. Нужен короткий проход на production-сборке с Network/Performance; React Profiler помогает отделить стоимость render, но сам добавляет overhead и по умолчанию выключен в production. Не выдавать сервисные миллисекунды за время открытия страницы. [React Profiler](https://react.dev/reference/react/Profiler).

## Bundle и React Doctor

Проверены существующие production-артефакты `.next/diagnostics/route-bundle-stats.json` и соответствующие chunks Next 16.4.1, без нового build. Сумма route initial JS: ученическая работа — около 886 КБ raw / 272 КБ локального gzip, статистика — 886/271 КБ, банк — 878/270 КБ, login — 770/231 КБ. Сюда входит общий React/Next runtime; это не дополнительный размер каждой страницы и не фактическая передача при тёплом кеше.

Часть chunks содержит общие схемы/Better Auth, но размер потенциально удаляемого кода не установлен. Прежде чем дробить shared-контракты, проверить import graph встроенным `next analyze`; установленная версия поддерживает analyzer без новой зависимости. Наличие пакета в package.json не доказывает его загрузку на странице. [Next bundle analysis](https://nextjs.org/docs/app/guides/package-bundling).

React Doctor изучен, не установлен и не запускался. Может быть полезен как разовая проверка React-кода с ручным разбором результатов; score не заменяет измерения. В [исследовании источников](2026-10-24-performance-references.md) описаны pinned source revision, сетевые функции и отключение telemetry/score/Socket для отдельного запуска. Runtime-зависимость, автоматические исправления и обязательный CI gate сейчас не обоснованы. [CLI reference](https://www.react.doctor/docs/reference/cli-reference).

## Границы результата

Найденные кандидаты ещё не реализованы; сравнения «до/после» нет. Не измерены end-to-end latency, HTTP auth/session, сеть до VPS, долгий конкурентный сеанс, браузерная память/long tasks, реальные изображения и большой накопленный каталог. По результатам текущих замеров не предлагаются смена HTTP framework, Redis, очередь, WebSocket, глобальные memo и виртуализация таблицы. Сначала три ограниченных изменения и профиль конкретного взаимодействия при необходимости.
