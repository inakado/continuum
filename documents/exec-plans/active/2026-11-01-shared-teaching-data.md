# Общая учебная база преподавателей

Статус: Active — реализация, ревью и локальные проверки завершены; выпуск по отдельной команде с восстановлением только вперёд. Дата: 01.11.2026. Production не меняется.

## Цель и основание

Требование пользователя: все преподаватели работают с общими материалами, банком задач, работами, учениками и результатами. Аккаунты остаются разными. Фактические права и production-срез зафиксированы в [аудите](../../research/2026-11-01-data-access-audit.md).

Эта целевая модель заменяет прежнее продуктовое предположение о личных библиотеках и банках. Действующие SoR-документы пока описывают реализованный код; их синхронизация входит в реализацию. Нельзя считать аудит доказательством готовности общей базы.

## Единый продуктовый контракт

| Область | Целевое правило |
| --- | --- |
| Материалы, включая черновики; банк, ключи и решения; библиотека работ и её архив | Одна общая база. Любой активный teacher видит и выполняет поддерживаемые операции независимо от автора |
| Классы, ученики, доступ к параллелям | Общие. У одного ученика одинаковые отметки доступа на экранах всех teacher |
| Назначения, выполнение, ответы, фото, баллы, статистика, опубликованные PDF | Все teacher могут просматривать общий учебный процесс через существующие интерфейсы |
| Авторство | Сохраняется как происхождение записи; не ограничивает предметный доступ. Само включение общей модели не меняет автора существующих объектов |
| Ученик | Видит опубликованные материалы разрешённых параллелей, только свои назначения, ответы, фото и опубликованные проверки; правильные ответы после завершения собственной тестовой части |
| Агент | Действует в пределах своего ключа и выбранных классов/учеников; доступ не зависит от автора работы. Его scope не расширяется до всей базы автоматически |
| Пароли, browser sessions, ключи устройств | Персональные; общая учебная база не раскрывает секреты другого аккаунта |
| Незавершённые загрузки, одноразовые секреты, receipts запросов | Принадлежат операции и её инициатору. Подтверждённая задача/работа становится общей; получение чужого временного ZIP-preview для этого не требуется |
| Admin | Текущая отдельная роль. Не включать автоматически teacher-права и не строить новый admin CRUD в этой инициативе |

Общий доступ teacher не вводит произвольное изменение сданных ответов или фотографий ученика. Баллы изменяются существующими процедурами исправления ключа и публикации проверки с ревизиями. Новый browser-редактор проверки развёрнутых задач не входит в переход.

## Понятные правила совместной работы

1. **Доступ к параллели:** любой teacher включает/выключает одну запись studentId + gradeBand. Повторное включение другим teacher не меняет библиотеку и не переписывает автора действующего grant без отдельной необходимости учёта. grantedById не участвует в выборе материалов. Зачисление/перевод использует ту же семантику; прежние доступы сохраняются по действующему правилу.
2. **Редактирование общей работы:** teacher B открывает работу A и меняет тот же объект. Отдельная вариация создаётся существующей кнопкой копирования; копия тоже общая. Прежние назначения сохраняют закреплённую версию.
3. **Два редактора:** запись с устаревшей ревизией получает 409. Интерфейс сохраняет несохранённый ввод и предлагает перечитать/согласовать изменения; автоматического перезаписывания чужой редакции нет. Полноценное одновременное редактирование как в Google Docs не требуется.
4. **Обновление списков:** общие списки/отчёты перечитываются при возвращении в окно и после локальных операций. Изменения другого аккаунта не должны бессрочно оставаться скрытыми в клиентском кеше. Обновление списка не заменяет содержимое редактора с несохранённым вводом; websocket-инфраструктура не нужна.
5. **Импорт одного пакета разными teacher:** один stableId обозначает одну задачу общей базы. Неизменённый повтор не создаёт дубль. Изменённый контент проходит явный preview и проверку baseline; изменение ключа уже выданных работ использует существующее подтверждаемое исправление, а не скрытый пересчёт обычным импортом.
6. **Исправление задачи:** охватывает совместимые связанные работы всех авторов по taskId. Условия/баллы обновляются существующим resolver; ответы, фото и immutable snapshots сохраняются. Перед подтверждением показан весь затрагиваемый scope, hash защищает от устаревшего preview.
7. **Архив и удаление:** состояние общее — если teacher архивировал работу, она в общем архиве. Удаление задания из банка сохраняет исторические ссылки. Работа с назначениями по-прежнему не удаляется; отзыв назначения остаётся отдельным явным действием с подтверждением последствий для всех его получателей. Сброс пароля и удаления учеников/классов сохраняют действующие подтверждения.
8. **Авторство и аккаунты:** деактивация автора не должна скрывать общие материалы от остальных teacher; отзыв его ключа прекращает только агентский доступ этого ключа. Не вводить новый флаг владельца, который снова разделит общую базу.

## Границы реализации

В scope: Library, Identity & Access grants, Assessment Bank/Works/Assignments/Statistics/Solutions, совместимые исправления и reviewer read-path, минимальные названия UI и обновление server state, договорённости о блокировках/идемпотентности, тесты и SoR.

Вне scope: организации/команды, приглашения, новые роли и ACL-редактор, персональные папки/архивы, live collaborative editor, новый интерфейс ручной проверки развёрнутой части, автоматическая публикация агентом, перенос файлов между S3-префиксами, новая система аудита всех действий.

Использовать текущий модульный монолит и role guards. В контентных read-path убрать зависимость доступа от автора; actorId оставлять в существующих операционных записях. Не вводить универсальный permission framework. Создатель, исполнитель операции и получатель результата — разные смыслы, их нельзя смешивать в одном teacherId-фильтре.

## Порядок выполнения и контрольные точки

### 1. Зафиксировать инварианты и исходные данные

- До кода составить список всех ownership-проверок: чтение, файлы, записи, импорт, копирование, архив, отзыв, preview исправлений и их подтверждение. Отдельно пометить проверки actor/receipt, которые остаются персональными.
- Проверить stableId во всём банке, включая удалённые записи, повторяющиеся названия/порядок разделов, существующие ссылки работ и S3. Не объединять разделы по одному названию и не пересоздавать задачи.
- Сохранить контрольные количества/ID и хеши тестовых ответов, фото и закреплённых snapshots для регрессионной проверки. Production-артефакты с персональными данными не помещать в Git.
- Результат этапа: однозначные целевые права и проверяемый список изменений, без неизвестных конфликтов идентичности задач.

### 2. Общие grants и библиотека

- Удалить фильтр автора из выдачи ученических gradeBands и чтения опубликованных материалов; сохранить публикацию, параллель и тип активного файла.
- Любой teacher меняет общий grant; повторный enable/зачисление не переключает библиотеку. Disable не возвращает ложный успех при оставленном grant коллеги.
- Teacher list/detail/PDF/upload/publish/delete работают с общей библиотекой. Существующие авторы и пути файлов сохраняются; проверка назначения загружаемого файла остаётся.
- Проверить общий порядок разделов/занятий при одинаковых sortOrder старых личных библиотек; чтение детерминировано, данные не сливаются автоматически.
- Приёмка: два teacher видят одинаковые grants; ученик с каждым из них получает те же опубликованные занятия; черновики и запрещённые параллели закрыты по прямой ссылке и PDF URL.

### 3. Общая идентичность банка и транзакции

- Предлагаемое ограничение БД: глобальная уникальность stableId вместо unique(teacherId, stableId). Сохранять task UUID, teacherId как автора, версии и ссылки. Перед миграцией проверять конфликты; при конфликте остановка с отчётом, без автоматического merge/rename/delete.
- Синхронно изменить preview/confirm, duplicates, поиск, topic/source facets, детали/рисунки, экспорт, delete/restore и validation исправлений. Временный import и retry receipt остаются у инициатора.
- Пересмотреть общие блокировки: текущая блокировка строки учителя не сериализует двух teacher общей базы. Согласовать один порядок bank → work → recipient для конфликтующих путей; включить composition/copy/assign, исправления и завершение попытки. Конкретный протокол зафиксировать до редактирования этих сервисов.
- Предпочтительный небольшой механизм для общего банка: транзакционные advisory locks с фиксированным ключом из policy; исправляющие записи исключают конкурирующий finish, а независимые finish могут использовать shared-lock. Применимость и полный список участников должны быть подтверждены concurrency-тестами, до этого это проектное предложение.
- Идемпотентность сохраняет смысл: повтор операции того же инициатора возвращает результат; общий предметный доступ не даёт права присвоить чужой requestId. Исторические receipts не переписываются.

### 4. Работы и весь связанный процесс

- Доступ к общей работе, разрешение task refs, сохранение, копия, версии, архив и удаление используют общую базу; revision/expected checks остаются.
- Назначения, список выполнения, статистика, детализация, CSV, фото и опубликованные PDF открываются всем teacher. Reviewer сохраняет ограничения конкретного ключа и публикации.
- Исправления ключа просматривают связанные версии всех авторов. Обычное изменение состава общей работы не переписывает старые назначения.
- До готовности всех этих путей не выпускать интерфейс с общими списками и недоступными по клику объектами.

### 5. Минимальный интерфейс и документация

- Вкладку «Мои работы» переименовать в «Библиотека работ»; общие текущие работы и архив используют существующие фильтры. Не добавлять набор новых статусов/вкладок.
- Удалить тексты «ваш банк» и аналогичные обещания личного владения там, где база стала общей. Не размещать обязательную подпись автора возле каждого элемента без практической нужды.
- Согласовать ошибки конфликта с изменением другим преподавателем, сохраняя текущие способы восстановления ввода.
- Обновить PRODUCT, CONTENT, ASSESSMENTS, SECURITY, ARCHITECTURE, FRONTEND и при необходимости REVIEWER-CLIENT; сгенерировать DB/API docs. Временные ограничения и результаты — только в плане.

## Проверки приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| A создал материал/задачу/работу; B открыл список, прямой URL и файл | Один и тот же объект доступен; B выполняет поддерживаемые изменения |
| A/B включают и выключают доступ одному ученику | Одни gradeBands и опубликованные материалы; автор выдачи ничего не переключает |
| Перевод/повторное зачисление другим teacher | История/ответы/старые назначения сохраняются, библиотека не меняется из-за автора |
| A/B одновременно импортируют один stableId | Одна задача, согласованные версии и предсказуемый конфликт; ни дубля, ни частичной записи |
| A/B одновременно правят одну работу | Одна запись проходит; устаревшая получает 409 без потери локального ввода |
| Исправление ключа одновременно со сдачей учеником | Согласованные итоги и все read-path, исходный ответ сохранён |
| A исправил задачу, включённую в работы A и B | Preview/пересчёт охватывает все совместимые ссылки |
| Delete/restore банка одновременно с составлением/копированием/назначением | Исторические версии читаются; новые ссылки не обходят действующий lifecycle |
| B читает и отзывает назначение A | Preview полного scope; отзыв только подтверждённого назначения, остальные данные сохранены |
| Ученик/аноним/admin пробует teacher URL; ученик открывает чужую попытку/фото/PDF | Доступ закрыт по роли/получателю, включая прямые ссылки |
| До/после завершения теста | answerKeys отсутствуют до завершения; после — только канонические ответы своей попытки |
| Агент другого teacher, scope включён/исключён, ключ отозван | Доступ зависит от актуального scope и состояния ключа, а не автора работы |
| Повтор запроса/смена аккаунта/удалённая запись | Нет дублирования, восстановления tombstone или раскрытия чужих временных секретов |
| Автор деактивирован | Общий контент доступен другим активным teacher, ключи автора не работают |
| Mobile/desktop, возврат в окно, открытый редактор | Общие данные обновляются; нет авторских 404, переполнений, самопроизвольной потери ввода |

API проверки — в локальном Docker с синтетическими пользователями/файлами. Отдельно unit/shared, API typecheck, web typecheck и role-specific tests, lint:boundaries, docs:check. Полный integration-набор должен проходить на зависимостях текущего lockfile; нельзя ослаблять проверку лимита или Origin ради выпуска.

## Риски и выпуск

- Потеря общего контента из-за снятия не всех ownership-фильтров, неверные ID при merge и гонки разных авторов — главные риски. Контрольные точки выше обязательны.
- Реализовывать последовательно локально, выпускать согласованный контракт целиком. Переход не должен включать незаявленную публикацию старых черновиков, изменение ответов, массовый пересчёт или отзыв назначений.
- Release только по отдельной команде. Перед production-миграцией — подтверждённая актуальная recovery-копия и штатные migration/CI gates по deploy runbook. Этот план не является разрешением на миграцию/деплой.
- Восстановление выполняется только вперёд: исправленная сборка работает на актуальной БД. Старый runtime и старый dump не возвращаются автоматически; ограничения схемы сохраняются.

### Инженерные основания и принятый протокол

- [Fowler: Workflows of Refactoring](https://martinfowler.com/articles/workflowsOfRefactoring/fallback.html): небольшие изменения под регрессией; переход к общей базе — изменение продукта, поэтому старые тесты персонального доступа заменяются явными межаккаунтными сценариями, а не механически удаляются.
- [Prisma: transactions, OCC, idempotency](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/transactions): сохраняем revision/expected checks и атомарность, при Serializable сохраняем ограниченные повторы; общая видимость не означает повторное использование чужого временного импорта.
- [PostgreSQL: explicit/advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html): один transaction-level ключ общего банка. Exclusive — import confirm, bank delete/restore и cleanup preview; shared — composition/copy/freeze/assign и student finish. Порядок bank → work (если требуется) → recipient; revoke/archive/delete работы используют только work → recipient и не приобретают bank позже. Preview пересчёта — RepeatableRead без удержания lock до подтверждения, актуальность защищена impact hash.
- Ключ блокировки задаётся одним helper в common; нет новой таблицы/permission framework. Lock автоматически освобождается при commit/rollback, shared finish разных учеников не сериализуются друг с другом.
- Миграция global stableId сначала проверяет коллизии, включая deleted, и останавливается с диагностикой. Ни ID, ни автор, ни версии существующих записей не переписываются. Локальные тестовые данные и production — разные контуры.
- Применяем Ponystack и Codebase Design: существующие read/write сервисы остаются; новая абстракция только для действительно общего протокола блокировок. Правила домена фиксируются в существующих CONTEXT/SoR, без второй карты терминов.
