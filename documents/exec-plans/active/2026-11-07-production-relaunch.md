# Чистый production-запуск: AdminVPS и Cloud.ru

Создан: 07.11.2026. Обновлён: 08.11.2026. Статус: по прямому поручению владельца выполняются переносимый deploy и выпуск приложения. Первый выпуск и обычное обновление завершены; приложение работает по HTTPS, два преподавателя входят. Материалы/S3 и продление TLS проверены, начальная копия БД восстановлена изолированно. Регулярный offsite recovery и приёмка 60 пользователей остаются открытыми.

## 1. Цель и принятые границы

Запустить Continuum на новом российском VPS, с новым доменом и отдельным S3, после недоступности Beget. Рабочий масштаб — до 60 одновременно активных учеников и два преподавателя.

Данные владельца от 08.11.2026: IPv4 нового VPS — `137.22.150.253`, домен — `cntm.space`; целевой origin — `https://cntm.space`. Проверены root SSH по новому ключу, Ubuntu 24.04 LTS x86_64, 4 vCPU, RAM 7,8 GiB, диск 79 GiB с 72 GiB свободными и swap 511 MiB. На момент проверки `deploy`, Docker, Node и Nginx отсутствуют. Подтверждены базовое имя S3-бакета `bucket-7aa489`, глобальное имя `cntm` и STANDARD; содержимое проверено временными объектами. Тарифная площадка и полный размер квот отдельно не аудировались.

**Уточнение владельца в этом чате:** старые данные не переносим. Нужны новая пустая БД, пустой application bucket и только два преподавателя: `inakado`, `lamuerte`. Не создавать старых учеников, демонстрационные аккаунты или отдельного администратора без нового решения. Это разрешение на проектирование чистого запуска, а не на удаление старых ресурсов Beget.

Исследование сохранено в этом плане и [отчёте провайдеров](../../research/2026-11-07-hosting-providers.md). Владелец затем самостоятельно зарегистрировал/оплатил ресурсы, создал ключи и установил SSH public key. Агент выполнил согласованную очистку прежних ключей и первичные S3-проверки; после прямого поручения владельца изменения приложения реализованы и отправлены в PR #15; CI и активация выполняются.

В scope реализации: VPS, DNS/TLS, первоначальная инициализация PostgreSQL, два teacher-аккаунта, S3, адаптация существующего выпуска, резервирование, мониторинг и приёмка.

Вне scope: восстановление Beget, перенос старых ответов/фото, новая архитектура приложения, Kubernetes, managed PostgreSQL, Redis, отдельный worker, CDN и постоянный второй application server.

## 2. Основания и текущее состояние

### Проверено в репозитории

- На момент анализа: ветка `codex/shared-teaching-release`, HEAD `b7cc82d`; локально много незакоммиченных изменений интерактивных лекций. Это **не** готовый проверенный release revision. Состояние удалённого main/CI и старого production в этом исследовании не проверялось.
- Runtime: Next.js standalone через systemd, NestJS API и PostgreSQL 16 через Docker Compose. Worker/Redis/TeX на сервере не нужны. Источники: `docker-compose.prod.yml`, `deploy/systemd/continuum-web.service`, `apps/api/Dockerfile`.
- Код приходит через Git; API и web собираются на VPS с кешем. CI хранит доказательство проверки состава исходников один день. Это не сохранённый готовый production-образ: холодному VPS нужен доступ к GitHub, registry пакетов, Docker registry и apt.
- API публикуется только на `127.0.0.1:3000`; web — `127.0.0.1:3001`. У PostgreSQL нет публичного published port. Nginx — единственная публичная точка приложения.
- S3 заменяется env-настройками: AWS SDK v3, `Upload`, GET/HEAD/DELETE, проверка bucket, подписанные GET. Production сам bucket не создаёт. Источники: `packages/shared/src/storage-core.ts`, `apps/api/src/infra/storage/object-storage.service.ts`.
- PDF открывается по краткоживущему presigned GET; фото и рисунки идут через авторизованный API. Загрузка файлов — через API. Открывать bucket или разрешать публичный ListBucket не требуется.
- Интерактив — самодостаточный ZIP; браузер запускает HTML/JS в `sandbox="allow-scripts"` iframe с запретом внешних сетевых обращений. Каждый запрос документа сейчас читает ZIP из S3, проверяет hash и распаковывает его в API; CDN-кеша в этом пути нет. Источники: `documents/INTERACTIVE-PACKAGE.md`, `apps/api/src/library/library-read.service.ts`, `interactive-archive.ts`, `apps/web/components/interactive-lesson/`.
- Реальные локальные пакеты: KIN-01 ZIP 958 969 байт, HTML 1 880 955 байт; KIN-02 ZIP 891 061 байт, HTML 1 631 156 байт. Это измерение файлов, не нагрузочный тест.
- `/ready` проверяет соединение с PostgreSQL, но **не S3**. Успешные `/health` и `/ready` не подтверждают работу материалов.

## 3. Рекомендуемая конфигурация

| Компонент | Решение | Причина |
|---|---|---|
| VPS | AdminVPS, российская площадка, KVM, x86-64 | Сохраняем текущий Docker/systemd-путь; не нужна адаптация под ARM |
| CPU/RAM | **4 vCPU / 8 ГБ** | Запас для холодной сборки Next/API и одновременных открытий лекций |
| Диск | **80–100 ГБ NVMe**, расширяемый | ОС, БД, pnpm store, BuildKit/Next cache, текущий и предыдущий runtime |
| ОС | **Ubuntu Server 24.04 LTS**, без панели сайтов | Предсказуемый apt/Docker/Nginx-контур; [Docker поддерживает эту ОС](https://docs.docker.com/engine/install/ubuntu/). Наличие образа уточнить у AdminVPS; 22.04 LTS допустима после проверки поддержки стека |
| IP/сеть | Один постоянный публичный IPv4; канал от 100 Мбит/с, лучше доступный 1 Гбит/с | Нужны входящий HTTPS и исходящий HTTPS до S3/registry; проверяем реальные ограничения тарифа |
| Swap | 2–4 ГБ, как аварийный резерв | Не заменяет RAM; постоянный swap во время работы — основание для исправления |
| S3 | **Cloud.ru Evolution Object Storage, STANDARD, многозонный** | Активные PDF/фото/ZIP; холодный/ледяной класс для них не подходит |
| PostgreSQL | 16, локальный Docker volume | Отдельный managed DB для этого масштаба не обоснован |
| Резервирование | Копии у двух провайдеров плюс контролируемая внешняя копия | Сбой одного управляющего контура не должен лишать исходных данных и всех backup |

2 vCPU/4 ГБ допустимы как экономичный runtime, но сейчас приложение ещё и собирается на VPS. Поэтому это не основной выбор. Переход на 16 ГБ или отдельную БД нужен по измерениям, а не из числа зарегистрированных учеников.

Ориентир распределения RAM: ОС/Nginx 0,5–1 ГБ; web/API суммарно 1–2 ГБ; PostgreSQL около 0,5–1 ГБ; оставшееся — файловый кеш и сборка. Это инженерная оценка, не измеренные лимиты контейнеров. Не задавать всему стеку жёсткие маленькие memory limits без профиля.

Под диск держать минимум 20 ГБ свободными перед сборкой, алерт при 75–80% заполнения. Сохранять существующую ограниченную очистку release/build cache; включить ротацию Docker/journald/Nginx logs. Не чистить Docker volumes общими prune-командами.

### Что означает нагрузка 60 пользователей

Демонстрации считают геометрию и анимацию в браузере; 60 открытых страниц не означают 60 постоянных CPU-задач на сервере. Тяжёлый момент — синхронное открытие лекции, вход и отправка фото/ответов.

При одновременном открытии нынешнего KIN-01 API прочитает примерно 57,5 МБ ZIP из S3 и отдаст не менее 112,9 МБ HTML до JSON overhead. Через канал 100 Мбит/с только передача такого объёма занимает теоретически около 9 секунд для всего потока; это не прогноз времени отдельного ученика. Через 1 Гбит/с сетевой потолок выше, но остаются задержка S3, распаковка и очереди API. Текущая Nginx gzip allowlist не включает library interactive GET — не считать, что большой JSON уже сжимается.

Поэтому 4/8 — обоснованная стартовая конфигурация, **не доказательство** прохождения теста 60 одновременных открытий. Если тест покажет проблему, сначала измерить S3/CPU/сеть; затем рассмотреть ограниченный кеш проверенного immutable-документа или безопасное сжатие конкретного ответа. Не включать общий кеш приватного API и не добавлять Redis заранее.

## 5. Что делает владелец

1. Зарегистрировать AdminVPS, включить доступную MFA, сохранить recovery-коды отдельно. Проверить цену первого месяца/продления, наличие 4/8/80–100, IPv4, backup и российскую площадку.
2. Заказать VPS с Ubuntu 24.04 amd64, без ISPmanager и готовых CMS. Узнать у поддержки условия vCPU, фактическую полосу/лимит трафика, DDoS-политику и резервирование именно этого тарифа.
3. Зарегистрировать Cloud.ru, выбрать **Evolution**, доступ физического лица/нужного договора и оплату. Не создавать VM, VPC или managed PostgreSQL только ради S3. Проверить лимиты STANDARD и способ включения квоты.
4. Зарегистрировать новый домен. Решить один canonical hostname: `<новый-домен>` или `app.<новый-домен>`. DNS желательно управлять вне Beget; можно у отдельного регистратора. Проверить ежегодное продление, а не только регистрационную акцию.
5. После получения VPS передать его IP, выбранный домен, конфигурацию и сведения о backup. Пароли, S3 SecretKey и приватные SSH-ключи не помещать в Git или публичные сообщения.
6. При настройке пользователей определить отображаемые имена двух преподавателей и передать/получить начальные пароли защищённым способом. Прежние production-пароли и ключи Beget не переиспользовать.

Никаких обязательных регистраций в платном CI, покупке wildcard-сертификата или отдельном почтовом сервере у проекта нет. Let's Encrypt достаточно; рабочая почта для уведомлений о домене/оплате остаётся нужна владельцу.

## 6. SSH и серверная база

Последовательность настройки (фактический прогресс — в decision log):

1. Создать на компьютере отдельную пару Ed25519 для нового VPS; сначала проверить, что выбранный файл отсутствует. Приватная часть остаётся на компьютере, защищена passphrase/agent; в панель или `authorized_keys` идёт только `.pub`. Существующие рабочие ключи не перезаписывать.
2. Сверить fingerprint SSH host key через консоль/панель провайдера, затем закрепить в `known_hosts`. Один `ssh-keyscan` без независимой сверки подлинность сервера не доказывает.
3. Первым административным доступом создать `deploy`, каталог `/srv/continuum`, key-only login и необходимые права Docker/systemd. Участие в docker group фактически даёт root-возможности — ключ выпуска хранить соответственно.
4. Проверить вход `deploy` во второй сессии; лишь затем запретить парольный SSH и обычный root-login. Сохранить возможность аварийной консоли провайдера.
5. Создать новый SSH alias `continuum-adminvps` с User deploy. Прежний alias/ключ `continuum-vps` удалён по прямой команде владельца. Release-клиент использует `SSH_TARGET`; прямой вход — пользователем deploy.
6. На VPS использовать отдельный read-only deploy key для приватного GitHub-репозитория. Это другой ключ, чем Mac → VPS. Не копировать на VPS персональный GitHub token или приватный ключ Mac.
7. Поставить Docker Engine + Compose/Buildx из официального apt-репозитория, Node 24.x и pnpm 10.11.1; согласовать Node patch с Dockerfile/CI. Обновлённый `bootstrap-vps.sh` использует официальный apt repository и настраивает deploy/firewall/systemd; прежний convenience script заменён.
8. Firewall: публично 80/443; SSH для административного доступа. Не открывать 3000/3001/5432/2375/9000. Учитывать [обход правил ufw опубликованными Docker-портами](https://docs.docker.com/engine/install/ubuntu/); сохранять loopback bind API и отсутствие publish PostgreSQL. Проверить IPv6 отдельно.
9. Установить время/NTP, security updates с контролируемым окном перезапуска, ротацию logs. Настроить только узкое sudo-право для `continuum-web`; не выдавать `NOPASSWD: ALL`.

GitHub `Deploy Production` необязателен: ручной CLI уже достаточен. Если включать workflow, нужны отдельные production secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Не переносить старое значение host key на новый сервер.

## 7. Cloud.ru S3: целевая настройка

Выбрать **многозонный STANDARD**; не путать с Advanced OBS и SINGLE/однозонным классом. Создать заранее уникальный private bucket, например `continuum-prod-<suffix>`, с обычным именем без точек. Списки пользователей и файлы учеников не публиковать.

Параметры приложения, **пример для Evolution**, без реальных секретов:

```dotenv
S3_ENDPOINT=https://s3.cloud.ru
S3_PUBLIC_BASE_URL=https://s3.cloud.ru
S3_REGION=ru-central-1
S3_BUCKET=continuum-prod-<suffix>
S3_ACCESS_KEY_ID=<tenant_id>:<key_id>
S3_SECRET_ACCESS_KEY=<key_secret>
S3_FORCE_PATH_STYLE=true
```

Endpoint в конфиге без имени bucket: path-style добавляет его сам. `S3_PUBLIC_BASE_URL` здесь означает доступный браузеру endpoint для подписывания, **не публичный ACL**. Подписанную ссылку нельзя потом заменять новым доменом/CDN, не пересчитав подпись.

`S3_ACCESS_KEY_ID` у Evolution — составной идентификатор, не один KeyID. Секрет создаётся для отдельного service account и переносится в закрытый `deploy/env/api.env`. Для runtime достаточно bucket-scoped чтения/записи/удаления и необходимых HEAD/multipart-операций; роли и границы — в исследовании. Проверить, что key не даёт управление остальными bucket/аккаунтом. Отдельный backup principal не разделяет runtime credentials.

В документации default-квота STANDARD указана как 0 ГБ: проверить именно свой аккаунт и установить/запросить, например, 100 ГБ. Это квота, а не обязательная покупка 100 ГБ. Контролировать положительный баланс: Cloud.ru предупреждает о блокировке операций при нулевом/отрицательном остатке и удалении ресурсов после 30 дней задолженности. Источник: [ограничения Evolution Object Storage](https://cloud.ru/docs/s3e/ug/topics/overview__limitations).

Для текущего приложения S3 CORS не нужен: браузер загружает файл в API, API пишет в S3; PDF открывается обычной навигацией. Если позже появится прямой browser PUT/fetch, добавить только нужные origins/methods, а не `*` заранее.

Версионирование application bucket по умолчанию оставить выключенным: приложение ожидает DELETE файла, а версии сохраняют старые персональные файлы и требуют отдельной политики retention. Object Lock также не включать на application bucket. Для отдельного backup bucket версии/защита удаления допустимы после согласования retention и проверки возможностей провайдера. Lifecycle не должен удалять активные PDF/фото/ZIP по возрасту. Правило очистки брошенных multipart uploads применить только после проверки поддержки.

### Обязательная квалификация до подключения учеников

- Реальные AWS SDK v3 HEAD bucket, PUT, multipart PUT для достаточно большого объекта, HEAD/GET, DELETE; сравнение SHA-256 и Content-Type.
- Работа signed GET по точному endpoint из браузера; срок действия, ResponseContentType, кириллица/имена файлов. Проверить чтение с телефона и школьной сети.
- Анонимные GET/list не открывают private материалы; отсутствующий объект не раскрывает чужие данные.
- Импорт/публикация/повторное открытие KIN-01 и KIN-02 через настоящий host; CSP/sandbox не ослаблять.
- Загрузка фото через API и повторное чтение, PDF и изображения задач, удаление тестовых объектов штатным путём.
- Фактическая совместимость AWS SDK checksum/chunked/multipart с Cloud.ru. Если обнаружится ошибка, локализовать и только затем вводить минимальную настройку SDK; заранее не отключать проверки целостности.
- Из AdminVPS измерить время S3 connect/GET/PUT и p95. Текущие defaults — 2 с connection / 5 с socket, maxAttempts=2; повышать их только по измерению, не прятать ошибки большими timeout.

Наличие слова S3-compatible в документации — основание для кандидата, но не результат этих проверок.

## 8. Новый домен, DNS, TLS и auth

Для одного canonical `<APP_DOMAIN>`:

| Место | Целевое значение |
|---|---|
| DNS A | IPv4 AdminVPS |
| DNS AAAA | Только если IPv6 действительно настроен и проверен |
| Nginx server_name / cert path | Новый canonical hostname |
| `BETTER_AUTH_URL` | `https://<APP_DOMAIN>` без `/api` и `/auth` |
| `WEB_ORIGIN`, `CORS_ORIGIN` | `https://<APP_DOMAIN>` |
| `NEXT_PUBLIC_API_BASE_URL` | `https://<APP_DOMAIN>/api` **при сборке web** |
| `APP_DOMAIN` выпуска | Тот же hostname |
| reviewer client | Новый base URL при новом подключении |

Сначала временный HTTP-only Nginx, DNS и доступ к ACME challenge; затем сертификат и финальный HTTPS template. Текущий template сразу ссылается на ещё несуществующие certificate files, поэтому включать его первым нельзя. HTTP-01 требует [входящего порта 80](https://letsencrypt.org/docs/challenge-types/). После настройки проверить timer Certbot и пробное продление.

Создать новый случайный `BETTER_AUTH_SECRET` не короче 32 символов и новый пароль PostgreSQL; env-файлы — с закрытыми правами. Согласовать `DATABASE_URL` и `POSTGRES_*` в обоих env: runtime Prisma и `/ready` используют разные способы получения подключения. Секреты не передавать как literal shell args и не печатать в логи.

Смена runtime env не меняет уже встроенный `NEXT_PUBLIC_API_BASE_URL`: нужна новая сборка. Пользователи входят заново; browser-local память интерактивов относится к origin и на новый домен не переносится автоматически.

Не переписывать систему релизов ради смены провайдера. Первоначальный режим должен включаться явно, проверять пустую целевую БД/отсутствие runtime и отказываться трогать непустую установку. Отсутствие таблицы миграций в существующей непустой БД не является разрешением начать сначала.

Первоначальный `PREPARE_ONLY=yes` требовал старый API; новый INITIAL_DEPLOY-путь устраняет этот пробел. Новые миграции применяются командой deploy, а не `migrate dev`, `db push` или reset. У существующей установки сохраняются `MIGRATIONS_APPROVED`/`BACKUP_CONFIRMED`; для новой пустой БД явно фиксируется отсутствие прежних данных вместо ложного заявления, что backup существует.

Выпуск должен содержать согласованный набор локальных интерактивных изменений: `git archive HEAD` не захватывает untracked/незакоммиченные файлы. До этого этапа выбрать release revision и провести CI; автоматически коммитить чужой working tree нельзя.

## 11. Резервирование после нового запуска

Разделение VPS и S3 уменьшает общий риск, но не делает копию: потеря VPS без dump лишает пользователей/ответов, потеря S3 — файлов. Provider snapshot с открытым PostgreSQL не заменяет проверенный логический backup. [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html) даёт согласованный снимок одной БД; он не включает S3 и глобальные роли.

Минимальная схема:

- Ежечасный `pg_dump -Fc` PostgreSQL 16, контроль завершения/читаемости, шифрование перед отправкой в отдельный private backup bucket Cloud.ru; локально короткий буфер на VPS. Внешний ключ расшифровки и аварийная инструкция — у владельца, вне VPS и Cloud.ru.
- Еженедельный provider snapshot VPS — дополнительное ускорение восстановления ОС. Уточнить у AdminVPS периодичность, глубину и сохранность при блокировке/удалении услуги.
- Ежедневный **согласованный полный recovery-набор**: кратко остановить API, чтобы остановились пользовательские записи и фоновые cleanup; снять dump и manifest/count/hash актуальных S3-объектов, сохранить их локальную копию, затем гарантированно вернуть API, в том числе при ошибке backup. Отправку готового набора во внешнее хранилище делать после возобновления API; задать максимальную длительность окна и алерт при незавершённой копии. На текущем небольшом объёме это проще сложного WAL/PITR и учёта версий. При росте измерить длительность окна и пересмотреть метод. Не останавливать PostgreSQL для логического dump.
- Согласованный набор хранить **вне Cloud.ru и VPS-диска**: например отдельное backup storage AdminVPS с клиентским шифрованием, плюс регулярно скачиваемая зашифрованная копия на компьютер владельца. Нельзя считать обычный FTP безопасным транспортом credentials; до выбора такого storage подтвердить FTPS/SFTP/TLS, иначе подобрать другой транспорт/провайдера. Не включать непроверенный FTP в обязательную схему.
- Пока независимое сетевое хранилище не подтверждено, допустима ручная выгрузка полного зашифрованного набора на компьютер после изменений; она не даёт автоматического ежедневного RPO. Спящий Mac не считается постоянно работающим backup-сервером.
- Предложение retention: 24 hourly DB-копии, 7 daily согласованных наборов, 4 weekly. Потребный объём считать по реальному bucket/изменениям и компрессии; 30 ГБ активных файлов × 7 полных копий не помещаются в backup-тариф 50 ГБ.
- Runtime S3 key не имеет прав на backup bucket; отдельные credentials для backup/retention. Даже при использовании одной Cloud.ru organization backup не защищает от отказа всего провайдера — поэтому нужна вторая копия у другой стороны.

Цели для согласования: **RPO ответов до 1 часа** при доступной Cloud.ru; **полный согласованный recovery до 24 часов потери** по daily-набору; при отказе Cloud.ru гарантия определяется последней проверенной внешней копией. RTO 4–8 часов — целевая оценка до drill, не обещание провайдера. Ежемесячно восстанавливать dump в отдельную БД и проверять чтение файлов из восстановленного набора. Один успешный upload backup не подтверждает восстановимость.

Перед массовым удалением/импортом и значимой миграцией — свежий согласованный набор. Retention backup персональных данных явно документируется; это не вечный архив удалённых фото.

## 12. Проверки и наблюдаемость

### Проверки будущих изменений

- Domain/release helpers: валидный новый hostname, ошибочный origin/path/shell metacharacters, согласованность web URL/manifest; прежний security gate не обходится.
- Cold-start: новая БД без API/`_prisma_migrations` запускается; непустая неизвестная БД отклоняется; повтор не дублирует teacher; ordinary deploy сохраняет checksum/history/forward-only.
- Учётные записи: ровно две teacher identities с профилями, корректный Argon2, отсутствие demo students/admin и паролей в логах; оба входа работают.
- Изменения backend — Docker build/typecheck/tests по контуру; frontend — boundaries, web typecheck/tests, desktop/mobile QA при затрагивании UI. В агентской sandbox не запускать `CI=true pnpm install --frozen-lockfile`.
- Release — обычные CI quality/security, schema history, health/readiness и полный S3 smoke. S3 квалификацию не заменять локальными MinIO-тестами.

### Нагрузочная приёмка на новом сервере

Только подготовленные тестовые identities/данные, с последующей штатной очисткой. Профиль 10 → 30 → 60 пользователей: login, каталог, одновременное открытие KIN-01, 10–15 минут чтения/сохранения ответов и ограниченное число реальных фото-загрузок. Не приравнивать 60 учеников к 60 запросам в секунду и не делать 60 непрерывных максимальных upload.

Отдельный worst case — 60 открытий лекции почти одновременно. Снимать p50/p95/p99, 5xx/429, CPU/RSS/GC/swap, свободный диск, PostgreSQL connections/locks, S3 latency. Предлагаемые критерии: без потери/перезаписи ответов и OOM; обычные API p95 до 1 секунды; открытие текущей лекции p95 до 3–5 секунд при согласованной тестовой сети. Медленную школьную сеть и общую серверную пропускную способность оценивать отдельно.

**Особый риск общего школьного NAT:** Better Auth настроен на `5` запросов `/sign-in/username` за `60` секунд и использует `x-real-ip`. Проверить входы нескольких учеников с одного публичного IP: возможные 429 нельзя объяснять слабым VPS. Если воспроизводится, исправить ключ/политику rate limit с сохранением защиты от перебора; не отключать limiter целиком. Источник: `apps/api/src/auth/better-auth.factory.ts`.

Минимальный мониторинг: внешний HTTPS/login и DB-ready раз в 1–5 минут, регулярная авторизованная S3-проба, CPU/RAM/disk, возраст последней успешной backup/restore-проверки, срок сертификата/домена и баланс обоих провайдеров. Наблюдатель должен находиться вне контролируемого VPS. Алерт — при реальной ошибке/просрочке, а не сообщение на каждый успешный опрос. Конкретный канал выбирает владелец; в этом исследовании никакие сообщения/автоматизации не создавались.

## 13. Риски и действия при сбое

| Риск | Действие |
|---|---|
| Цены/доступность AdminVPS отличаются от индекса | Подтвердить корзину и поддержку перед оплатой; сначала один месяц |
