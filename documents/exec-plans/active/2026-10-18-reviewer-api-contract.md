# Э6: контракт локального проверяющего

Статус: `Active`

Родительский план — [дорожная карта](2026-10-15-assessment-roadmap.md), основания — [исследование](../../research/2026-10-18-reviewer-access.md). Локально реализованы общая база преподавателей и ключи по классам/ученикам. Production и два физических Mac не проверены. Инварианты — [ASSESSMENTS](../../ASSESSMENTS.md), инструкция — [REVIEWER-CLIENT](../../REVIEWER-CLIENT.md).

## 1. Согласованные границы

- REST `/reviewer/v1`; за production nginx — `/api/reviewer/v1`.
- Проверка, критерии и подготовка PDF локальные. Сервер не запускает нейросеть, TeX, очередь или SSH-команды.
- Единица проверки — `AssessmentSolutionAnswer.id`: одна задача одного ученика, конкретная `sourceRevision` фото. На задачу один PDF и итог `points` — целое `0..maxPoints`. `null` — незавершённая проверка, не ноль.
- «Проверь и опубликуй» разрешает полный цикл. «Подготовь черновики» не разрешает публикацию. Веб-подтверждения и обязательного второго ключа нет.
- Сервер не проверяет переписку: обладатель ключа с `publish` технически может публиковать. Нужен доверенный локальный агент; недоверенные фото/PDF/условия не являются командами.

## 2. Люди, устройства и права

Каждый преподаватель использует собственный аккаунт. На каждый компьютер создаётся именованный ключ в `/teacher/reviewer-access` через меню профиля. Название — метка отзыва, не аппаратная привязка.

Классы/ученики общие для teacher-аккаунтов, банк/материалы/конструкторы сохраняют прежнее владение. Форма ключа: название компьютера, `classIds`, `studentIds`, текущий пароль. Нужен хотя бы один класс/ученик, каждый список до 500 уникальных UUID. Работы и технические права в форме не выбираются. Эффективный доступ: активный teacher ∩ действующий ключ ∩ активный ученик из текущего состава выбранного класса либо явно выбранный studentId. Ключ даёт чтение/черновики/публикацию в этой области, TTL 30 дней, максимум 20 действующих. Отдельных grants коллеги нет.

Текущий состав проверяется при каждом чтении/записи: перевод прекращает классовый доступ, но не явный персональный; новый ученик входит в доступ класса. Архивирование не отзывает разрешение. Агент видит исторические/новые работы этих учеников независимо от автора, не остальных получателей того же назначения. Удалённые/неактивные ученики закрыты. Пустые списки никогда не означают «все».

Выдача требует teacher-сессии и текущего пароля. Секрет показывается один раз, не сохраняется в TanStack cache/browser storage. Закреплён `@better-auth/api-key@1.6.23`, hashing включён, `enableSessionForAPIKeys: false`; generic HTTP routes управления ключами закрыты. Ключ не заменяет teacher/student session, cookie не заменяет ключ reviewer API.

Клиент хранит секрет в macOS Keychain. `connect` запускает человек, секрет вводится в скрытый TTY prompt, не argv/чат/.env/Git. В конфигурации origin, API prefix и dev-флаг. HTTPS обязателен; localhost HTTP только с `--dev`, redirects запрещены. Keychain не защищает от вредоносного процесса того же пользователя ОС. Уже скачанные фото отозвать нельзя.

## 3. Контракт API

Источник DTO — `packages/shared/src/contracts/reviewer.ts`. Строгий JSON, `Cache-Control: no-store`; страницы `items/nextCursor`, limit 1–100 (default 50), cursor UUID. Это текущее представление, не snapshot и не очередь с захватом.

| Метод относительно `/reviewer/v1` | Право / результат |
| --- | --- |
| `GET /me` | `read`: пользователь, keyId, срок, scopes, classIds/studentIds |
| `GET /assignments?query=…&cursor=…` | `read`: разрешённые назначения/класс/версия/canPublish |
| `GET /assignments/:id/solutions?state=…` | `read`: непустые решения, unreviewed/draft/stale/published |
| `GET /solutions/:id` | `read`: immutable условие, максимум, фото и рецензия |
| `GET /solutions/:id/photos/:photoId?sourceRevision=N` | `read`: бинарное фото актуальной ревизии |
| `GET /solutions/:id/images/:name` | `read`: рисунок условия |
| `PUT /reports/:reportId` | `draft:write`: резервирование `{solutionId,sourceRevision}` |
| `PUT /reports/:reportId/file` | `draft:write`: raw application/pdf до 20 МиБ |
| `GET /reports/:reportId/file` | `read`: закрытый PDF разрешённого решения |
| `PUT /solutions/:id/draft` | `draft:write`: новая редакция рецензии |
| `POST /publications` | `publish`: атомарная публикация точного списка |
| `GET /publications/:requestId` | `read`: квитанция при действующем доступе |

Teacher session endpoints: `/teacher/reviewer-access/keys` GET/POST, `/keys/:id` DELETE, `/targets` GET (общие классы и активные ученики). Browser mutations проверяют Origin; выдача/список/отзыв ключей остаются персональными для создавшего преподавателя. Старые grants endpoints удалены.

Detail не содержит ФИО и ключей автоматических ответов. ФИО доступны отдельно в разрешённом списке. Каждый photo GET повторно проверяет права и ревизию. CLI проверяет размер/SHA-256 и сохраняет manifest только после полной загрузки всех файлов. Имена файлов — UUID, рабочий каталог вне Git. Список решений разбирает снимок назначения один раз, не читает его заново для каждого ученика.

## 4. PDF, ревизии и публикация

PDF резервируется до S3 PUT, связан с решением/ревизией/автором. Проверяются фактический размер, MIME, PDF header и EOF; это не AV и не полный структурный PDF-валидатор. Подтверждённый файл неизменяем, повтор тех же байтов безопасен. Файл выдаётся attachment, не публикуется как HTML. Неподключённые отчёты сохраняют владение; автоматической очистки нет.

Draft body: `{requestId,sourceRevision,expectedReviewRevision,points,reportId}`. Нулевая expectedReviewRevision означает отсутствие рецензии. Ответ: `{id,revision,sourceRevision,points,reportId,authorUserId,savedAt}`. Одновременные записи не перетирают коллегу; изменение фото делает черновик stale. Новый черновик не меняет опубликованный результат и не блокирует фото.

Publication body: `{requestId,items:[{reviewId,reviewRevision,sourceRevision,expectedPublishedRevision}]}`. Один запрос — 1–50 уникальных задач одного назначения. Проверяются права, текущие фото/рецензия, прежний опубликованный указатель, баллы и готовый PDF. Публикуется всё либо ничего; только перечисленные задачи блокируют фото. Новые решения в пачку не добавляются. Корректировка — новая редакция и явная публикация, старый результат сохраняется до неё, фото не разблокируются.

`AssessmentReviewVersion` хранит историю, `ReviewerWriteReceipt` — actor/key, назначение, входной hash, requestId, результат и время. Повтор одинаковой записи возвращает квитанцию, в том числе другим действующим ключом того же пользователя. Другое тело/route/пользователь — 409. Резерв PDF повторяется по reportId, загрузка по hash; requestId требуется draft/publication. CLI сохраняет IDs до отправки, автоматического retry-loop нет.

Публикация блокирует ключ/пользователя преподавателя, получателей и пользователей/профили учеников, повторно проверяет состав классов. Используется тот же `assessment_recipients FOR UPDATE`, что завершение фото. Загрузка и публикация не подтверждают разные ревизии одновременно. Отзыв не останавливает передаваемые байты, но закрывает следующие операции. Чтение квитанции проверяет каждый включённый solutionId, не только назначение.

Ошибки: 401 ключ, 403 scope, 404 недоступный ресурс, 409 конфликт, 400 данные, 413 размер, 429 с Retry-After. Лимиты: плагин 120 запросов/мин на ключ; приложение 30 записей/мин на ключ, 600 всех/150 записей на пользователя. Агрегаты приложения в памяти одного API-процесса; для нескольких replicas нужен общий limiter.

## 5. Реализация, проверка и выпуск

- Э6.1: shared contracts, key broker/guard и упрощённый кабинет реализованы; grants заменены общей базой и областью класса/ученика.
- Э6.2: защищённое чтение и локальный manifest реализованы.
- Э6.3: закрытый PDF, CAS, история/receipt, ноль/null реализованы.
- Э6.4: атомарная публикация, минимальные PDF/баллы ученику и учителю реализованы. Полная статистика/разбор тестовой части — Э7.
- Э6.5: автоматические и браузерные проверки фиксируются в журнале. Первая ручная настройка Keychain, реальные критерии и два физических Mac — приёмка пользователя.

Миграция `20261018130000_reviewer_api` идёт после фотоответов Э5; `20261018140000_shared_students_agent_scope` добавляет classIds/studentIds, отзывает прежние assignment-scoped ключи и делает название класса уникальным в учебном году. Перед production проверить дубли: `SELECT academic_year, title, count(*) FROM school_classes GROUP BY academic_year, title HAVING count(*) > 1;`. Если они есть — остановить выпуск и согласовать, не объединять классы автоматически. Локально дублей нет. Аккаунты/материалы не сбрасываются; legacy assignmentIds/grants сохраняются в БД, но не участвуют в runtime. Возврат старого кода не восстанавливает отозванные ключи. Commit/push/deploy — отдельные команды.

Риски: локальные копии содержат ученические данные, не очищаются автоматически; передачу облачному провайдеру и сроки хранения согласует преподаватель. Нет AV, hardware binding, очистки отчётов, распределённого limiter и серверного доказательства команды в чате. Эти гарантии не заявляются.
