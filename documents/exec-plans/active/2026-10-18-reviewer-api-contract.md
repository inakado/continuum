# Э6: оставшаяся приёмка локального проверяющего

Статус: Active — приёмка пользователя на двух физических компьютерах.

Контракт реализован и описан в [ASSESSMENTS](../../ASSESSMENTS.md) и пересылаемом [REVIEWER-CLIENT](../../REVIEWER-CLIENT.md). Технические решения и прежние проверки — в [истории](../completed/2026-10-24-reviewer-implementation-history.md). Этот план не предлагает снова писать API или подтверждать публикацию в кабинете.

## Что проверить

1. На компьютере каждого преподавателя настроить отдельный ключ в системном хранилище по инструкции. Не хранить секрет в проекте, Markdown, ZIP или истории команд.
2. На реальном назначении проверить чтение разрешённых классов/отдельных учеников и отказ для чужой области. Перевод ученика проверять с учётом различий класса и персонального доступа.
3. По команде в чате получить конкретные ревизии фотографий, локально подготовить PDF и баллы каждой задачи, загрузить черновики. Ученик их ещё не видит.
4. После просмотра преподавателем по отдельной команде в чате опубликовать конкретные рецензии. Ученик получает PDF/балл; фото проверенной задачи фиксируются.
5. Повторить запрос после обрыва; проверить устаревшую ревизию фото и отзыв одного ключа. Второй компьютер должен продолжать работать со своим ключом.

## Критерии и ограничения

На обоих физических устройствах подтверждены read → draft → publish → receipt и отзыв. Автоматические HTTP/S3-тесты не заменяют эту пользовательскую приёмку. Локальные копии содержат ученические данные: преподаватель определяет сроки хранения и допустимость отправки внешнему провайдеру. Нет серверного доказательства команды в чате и аппаратной привязки ключа.

Выпуск сайта — отдельно по [deploy runbook](../../../deploy/README.md), без сброса существующих аккаунтов и материалов. Реальные ключи в журнал не записывать.
