# Конкурентное назначение и массовое создание учеников

Статус: завершено локально 21.10.2026. Commit/push/deploy не выполнялись.

## Цель и границы

Устранить HTTP 500 при конфликтах сериализации в двух write-контурах. Сохранить Serializable, атомарность, requestId/inputHash, снимки получателей и однократную выдачу паролей. Без миграций, UI, глобального retry всех запросов и изменения прав.

## Шаги и приёмка

1. Зафиксировать regression для raw adapter `40001`, ограниченного повтора и исчерпания.
2. Переиспользовать узкий DB retry: вся транзакция, пять попыток, backoff вне транзакции; после исчерпания — 409.
3. Проверить конкурентные одинаковые/разные запросы, конфликт payload и повтор после успеха. У назначения не появляются новые получатели; у учеников не появляются дубли и повторные пароли.
4. API unit, integration (параллельно и последовательно), Docker typecheck/build, boundaries/lint/docs.

## Решения и доказательства

- 21.10: новые unit-regression падают на прежнем коде: raw adapter не распознан; classTransaction не обрабатывает эту форму. Изолированный исходный school-classes suite прошёл 4/4; прежний intermittent failure не выдаём за постоянный.
- В classTransaction уже был немедленный retry P2034 до трёх попыток: прежняя запись техдолга о полном отсутствии retry устарела. Необходимо обрабатывать raw adapter и ограничивать исчерпание, не ослаблять изоляцию.
- Повторяется только известный rollback: Prisma P2034, PostgreSQL 40001/40P01 в известных формах; дополнительно существующая коллизия логина в classTransaction. Не повторять сетевые/неизвестные ошибки с неоднозначным commit.
- Источники: [Prisma transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions), [PostgreSQL isolation](https://www.postgresql.org/docs/16/transaction-iso.html). Повтор включает всю бизнес-транзакцию и новый snapshot.

## Риски и откат

Высокая длительная конкуренция всё ещё может дать 409, но не частичный результат. Argon2/случайные пароли готовятся до транзакции и переиспользуются только внутри одного вызова; исходные пароли не сохраняются. Откат — только изменения retry и тестов этого плана; чужой working tree сохраняется.

## Проверки

- До исправления два новых unit-regression упали на raw adapter error; после исправления — зелёные.
- Полный API unit-suite: 82/82. Проверены известные формы serialization/deadlock, паузы, предел пяти попыток, отсутствие retry для бизнес-ошибок/неоднозначных соединений и 409 после исчерпания.
- HTTP/PostgreSQL: четыре одновременных одинаковых назначения создают одну версию и одну квитанцию; разные классы назначаются конкурентно; один requestId для разных работ возвращает 201/409 без частично созданной второй версии. Существующие проверки stale roster, новых учеников, отзыва и повторного назначения сохранены.
- Массовое создание: шесть разных пакетов с одинаковыми фамилиями получают 12 разных логинов; повтор всех пакетов возвращает прежние ID без credentials. Два одинаковых конкурентных запроса создают один пакет; одинаковый ключ с разными данными — 201/409 и один атомарный набор.
- Полный параллельный integration-suite: 52/52, затем 53/53 после расширения проверки независимых назначений. Полный serial-suite: 52/52, финальный расширенный прогон 53/53. Ошибки прежнего QA UX-04 остаются историей того прохода, не переписываются задним числом.
- Docker API typecheck/build, `pnpm lint:boundaries`, `pnpm lint`, `pnpm docs:check`, `git diff --check` прошли. В lint остаются прежние complexity warnings; новых нет. UI не менялся, браузерная/mobile QA не проводилась.
- Ponystack-contract: один узкий helper для двух существующих retry-контуров, без новых зависимостей, конфигурационных слоёв и глобального Prisma middleware. Проверки безопасности/rollback не сокращались.
