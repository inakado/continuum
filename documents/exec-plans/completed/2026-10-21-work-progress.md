# UX-04 — состояния теста, фото и опубликованной проверки

Статус: completed — UX-04 реализован и проверен локально; ограничения общего API-suite ниже. Основание — подтверждённый пользователем [вариант](../../research/2026-10-21-work-progress-states.md).

## Scope и решения

- Три существующих места: список работ ученика, отчёт преподавателя, список назначений. Без новых страниц/вкладок, badge-набора и линейного stepper.
- Серверная read-проекция `progress`: число задач с подтверждёнными неудалёнными фото, число актуальных опубликованных проверок, готовность результата. Ученический черновик рецензии не раскрывается; 0 баллов считается опубликованной проверкой.
- Назначения агрегируются по исходным получателям версии, а не фото или текущим классам. Пустая часть не выдаётся за выполненную.
- Общий статус/счётчики не сохраняются в БД; миграции не нужны. Существующие write/API публикации не меняются.
- В mixed-отчёте пять колонок, состояние/заполнение/балл теста в одной. Мобильные строки имеют явные подписи. Существующий фильтр уточняется до «Тестовая часть» и скрывается при её отсутствии.
- Список ученика сохраняет количество верных ответов, не вводит новый суммарный балл. «Добавить решения» ведёт к задаче без фото, «Продолжить» сохраняет последнюю открытую задачу.

## Порядок и проверки

1. Proof-first: усилить реальный HTTP-тест публикации и наблюдать отсутствие progress до реализации.
2. Shared-контракты и пакетная API-проекция; затем role-specific UI и переход к фото.
3. Shared/API/web тесты: автоматическая/развёрнутая/смешанная работа, частичная публикация, нулевой балл, неподтверждённые фото, новая черновая редакция после публикации, права, скрытые отсутствующие части, фильтры и CTA.
4. Typecheck/build API только в Docker, web typecheck/test/build, boundaries, docs checks; desktop/mobile во встроенном браузере на изолированных fixtures.
5. Локальный review и Ponystack-contract; обновление SoR/roadmap. Никаких commit/push/deploy без отдельной команды.

## Риски и откат

- Новые обязательные read-поля требуют совместного выпуска API/web; старый API не должен молча отображаться как нулевые проверки.
- В момент публикации данные могут обновиться к следующему polling. UI не обещает push; активные списки/отчёт обновляются раз в 10 секунд.
- Существующий dirty tree сохранён; текущая ветка `codex/school-classes`. Связанные изменения выполняются последовательно: shared/read-контракты и singleton API/browser исключают независимую shared-workspace волну.
- Откат — код read/UI без отката данных; пользовательские работы/ответы/файлы не изменяются.
