# Смысл отметки работы в списке

Статус: Completed (локальная реализация, без deploy).

## Цель и объём

Заменить ошибочный «Черновик» фактической отметкой «Не назначена» / «Назначена» в списке работ. Архив — отдельный признак хранения. Не добавлять статусы редакций, исправлений, готовности или завершения. В редакторе убрать технический «Черновик». API — только read-поле списка, без миграций и изменения назначения/ответов.

## Семантика и референсы

- [Shopify Badge](https://shopify.dev/docs/api/app-home-ui-extension/latest/web-components/feedback-and-status-indicators/badge): краткая подпись сообщает фактическое состояние объекта. Для Continuum достаточен существующий обычный текст; цветные бейджи и новые фильтры не нужны.
- [Wayground Reports](https://help.wayground.com/support/solutions/articles/158000404058-reports-on-wayground): выдача активности и результат её прохождения рассматриваются отдельно. Адаптация Continuum: наличие назначения не зависит от завершения учениками.
- «Не назначена» означает отсутствие сохранившихся назначений любой версии. После удаления последнего назначения подпись возвращается к этому значению; слово «ещё» не используем.
- «Назначена» означает наличие хотя бы одного назначения любой версии. Обычное редактирование и presentation corrections не меняют отметку.
- Архивирование не отзывает выданную работу. Подпись назначения сохраняется рядом с отдельной отметкой «Архив».

## Шаги и проверки

1. Добавить обязательный `hasAssignments` в DTO списка из уже существующего агрегата; не выводить статус из права `canDelete`.
2. Обновить подписи списка/редактора и инвалидировать список после назначения.
3. Проверить runtime-контракт, projection, assigned/unassigned/archive UI и cache, затем desktop/phone во внутреннем браузере.
4. Обновить профильные SoR и generated docs; завершить план после проверок.

## Риски и rollback

Frontend требует новый list DTO, поэтому поставляется вместе с API. Данные и снимки не меняются. Rollback — возврат read-поля и подписей; операции сохранения и назначения остаются прежними. Push/deploy не входят в задачу.

## Результат и проверки

- API возвращает `hasAssignments` из существующего `_count.versions` с `assignments.some`; дополнительного запроса нет. Runtime-контракт списка требует boolean. Схема БД, detail/write DTO и снимки не меняются.
- В списке две обычные текстовые подписи; архив остаётся независимым. В редакторе технический «Черновик» удалён, сообщения автосохранения сохранены. Назначение инвалидирует list cache только после успеха; неопределённая ошибка не меняет отметку заранее.
- API unit: 95 тестов; Docker API typecheck прошёл. Отдельная проекция покрывает ноль/несколько назначенных версий, редактирование и архивирование. DB-query не изменён; новых интеграционных записей в БД не создавалось.
- Shared: 71 тест и typecheck; новый тест отклоняет отсутствующий/string `hasAssignments`, не подставляет значение из `canDelete`.
- Web: 286 тестов; typecheck и boundaries прошли. Покрыты обе подписи, неизменность после редактирования, независимость архива, отсутствие технического статуса в редакторе и invalidation после успешного назначения/сетевого повтора.
- Во внутреннем браузере проверены реальные `TeacherWorksScreen` и `TeacherWorkScreen` с синтетическими read-only API данными: 1280×800 и 375×812. Нет горизонтального overflow; архив показывает «Назначена · Архив», редактор не показывает «Черновик» или отметки изменений. Проверка не является production smoke. Временный стенд после QA удалён; PNG остаются вне репозитория.
- FRONTEND и ASSESSMENTS обновлены. `pnpm docs:generate`, `pnpm docs:check` и `git diff --check` выполнены; generated-файлы не изменились.

Frontend и API следует доставлять совместно: новый frontend требует `hasAssignments` в списке. Никаких новых пользовательских операций или настроек нет.
