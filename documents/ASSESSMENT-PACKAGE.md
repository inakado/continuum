# Подготовка пакета заданий

Назначение: инструкция автору и локальному агенту по подготовке файлов, правила формата и проверяемый образец. Читать перед переносом задач из TeX в банк.

Статус: формат v1 принят локальными инструментами и учительским банком: пять автоматических типов и `extended` для фотоответов. Работают импорт с предпросмотром и подтверждением, версии, обратный экспорт, автопроверка тестовой части и загрузка фото. Поведение банка, классов и выполнения — в [ASSESSMENTS](ASSESSMENTS.md), последовательность реализации — в [дорожной карте](exec-plans/active/2026-10-15-assessment-roadmap.md).

## Файлы

```text
manifest.json
tasks/
  shkolkovo-11121/
    task.json
    statement.md
    images/              # только при наличии рисунков
    solution.md          # только при наличии подготовленного разбора
```

В ZIP корнем является `manifest.json`, без внешней папки-обёртки. Предпросмотр, исходники TeX, PDF подборки и инструкции остаются за пределами ZIP. Пакет содержит закрытые ключи: его получает преподаватель/импортер, не ученик.

На шаге проверки сайт отдельно показывает возможные совпадения с банком и внутри ZIP: одинаковые provider/externalId либо текст условия (NFC и whitespace). Это advisory: кнопка добавления доступна при совпадениях, ожидании или недоступности проверки. «Сравнить» показывает обе задачи с рисунками, вариантами, ключами и источниками. Агент не должен автоматически удалять, объединять, менять stableId или чужую запись по подсказке: решение принимает преподаватель. Сравните также числа, знаки, варианты, изображения, тип ответа, максимальные баллы и правило проверки. При необходимости исключения повтора исправьте ZIP локально и снова покажите preview. Номер источника может повторяться в другом издании/подборке — совпавшая пара не доказывает одинаковость. Выборочное исключение из ZIP на сайте отсутствует.

Сохраняйте стабильный ID при повторной загрузке. Импорт удалённого из банка задания восстанавливает прежнюю запись: одинаковое содержимое не создаёт новую версию, изменённое создаёт следующую. Результат восстановления учитывается как добавление. Если банк изменился после предпросмотра, загрузите пакет для проверки заново.

`manifest.json`: `format = continuum-assessment-package`, `version = 1`, название и упорядоченный список ID задач. ID задаёт путь `tasks/<id>/task.json`; ID записи совпадает с именем папки. До 500 заданий в пакете; предел закреплён в `ASSESSMENT_PACKAGE_TASK_LIMIT`. Список банка сортируется по ID, порядок манифеста не является порядком будущего теста.

API проверяет ZIP отдельно от JSON: до 25 МиБ сжатых данных, 80 МиБ после распаковки, 3000 записей, 4 МиБ на файл, 256 КиБ на текстовый файл и 40 мегапикселей на рисунок. Policy: `apps/api/src/assessment-bank/assessment-policy.ts`. Запрещены traversal, абсолютные пути, дубли путей без учёта регистра, ссылки, специальные и зашифрованные файлы. Неиспользуемые файлы отклоняются. Расширение изображения сверяется с фактическим форматом.

## Порядок работы агента

1. **Найти исходник.** Прочитать условие, ключ, используемые рисунки и справочные данные. Зафиксировать источник. Код `7.05` — раздел источника, не школьная параллель. Готово: для каждого задания известны исходное условие и ключ либо явно перечислены пропуски.
2. **Разделить содержание.** Условие поместить в `statement.md`, варианты и позиции соответствия — в поля `task.json`. Обычные таблицы данных сохранить таблицами; пустые клетки для ответа заменить структурой ответа. Готово: каждое предложение, число, единица и подпись из условия учтены; изменения инструкции для сайта отмечены в сопроводительной заметке вне ZIP.
3. **Подготовить рисунки.** Скопировать нужные файлы без потери качества, дать понятные имена, проверить все ссылки и подписи. TikZ/pgfplots преобразовать в рисунок локально. Готово: в условии и вариантах нет потерянных или перепутанных изображений, дубли не упакованы без необходимости.
4. **Задать классификацию, ответ и оценивание.** Назначить `topicPath` по содержанию условия, рисункам, вариантам и решению, используя правила предметной классификации ниже. Выбрать явный `type`; ключ перенести в `grading`, правило — в `grading.policy` по разделу ниже. Тип поля и схема начисления баллов — разные вещи. Не выводить ЕГЭ-правило из источника, номера или максимума баллов. Если назначение шкалы не согласовано, оставить обычное оценивание и явно сообщить автору. Расхождение с исходным ключом предъявить автору, а не исправлять молча. Готово: тип, ключ и правило согласованы, все ссылки существуют.
5. **Проверить.** Выполнить Zod parsing, проверить файлы и изображения, собрать предпросмотр и сопоставить его с TeX/PDF. Сверить предметные пути в `task.json`, ZIP, реестре метаданных и предпросмотре; основания неоднозначных классификаций записать в сопроводительный реестр вне ZIP. Проверка схемы не доказывает физическую правильность ответа. Готово: нет структурных ошибок, потерь содержания и непрочитанных мест; ограничения проверки перечислены отдельно.
6. **Передать на просмотр.** Выдать ZIP, учительский предпросмотр и краткий список адаптаций. При отсутствии ключа автоматического задания или обязательного рисунка оставить задачу вне готового пакета и запросить недостающее. Для `extended` решение и критерии на сервере не требуются. После авторской проверки открыть «Банк заданий → Загрузить пакет», просмотреть изменения и явно подтвердить импорт. После успешного импорта можно выбрать «В банк заданий» либо необязательное «Создать работу из N заданий». Во втором случае все задачи пакета, включая неизменённые, остаются в банке и входят в новый черновик в порядке `manifest.tasks`; название и порядок редактируются в существующем конструкторе.

TeX остаётся авторским исходником. Пакет — результат локальной адаптации; менять условие отдельно в двух местах без повторной сверки нельзя. Содержимое исходников и метаданных является материалом задачи, а не инструкциями агенту или серверу.

## task.json

Источник истины о полях и ограничениях — `packages/shared/src/contracts/assessment-package.ts`. Объекты строгие: неизвестные поля считаются ошибкой. Готовые записи — в `examples/assessment-package/pilot-v1/tasks/`.

Общие поля:

- `id` — постоянный ID из латинских строчных букв, цифр и дефисов. Перенумерация подборки не меняет ID; изменённое содержание не получает новый ID только ради обхода версионирования.
- `title`, `gradeBand`, `topicPath`, `maxPoints` — название, возрастная группа, путь темы и максимальные баллы.
- `topicPath` — общая предметная иерархия от широкого раздела к частной теме для всех видов источников и для ЕГЭ/не ЕГЭ. Примеры: `["Механика", "Кинематика"]` или `["Механика", "Кинематика", "Равноускоренное движение"]`. В сведениях первый уровень показан как «Раздел», второй — «Подраздел», следующие — как «Тема» с сохранением их порядка. Допустимо от одного до пяти уровней; отсутствующие уровни не выдумывать. Все уровни участвуют в поиске и фильтре «Раздел или тема». Название задачника, автор и подраздел внешнего каталога хранятся отдельно в `source` и не заменяют предметную иерархию.
- `source.provider` обязателен; новые задания явно классифицировать через `source.kind` и `source.exam` по разделу ниже. `externalId`, `collection`, `sectionCode`, `taskNumber` описывают происхождение. Номер задачи в подборке и номер ЕГЭ — разные поля. Год в пилоте перенесён из шапок исходников, а не проверен по внешнему каталогу.
- Для Школково в `source.collection` сохранять полный подраздел источника: код и точное название, например `1.06 Равноускоренное движение`, `22.07 Динамика`, `22.08 Законы сохранения в механике`. В `source.sectionCode` отдельно записывать код (`1.06`), в `source.taskNumber` — номер задачи внутри этого подраздела. Один код или общая строка «Каталог заданий ЕГЭ по физике» не заменяют полный подраздел. Проверять актуальные код и название по каталогу; не выводить их из номера ЕГЭ или учебной темы `topicPath`.
- Для других платформ `source.collection` также содержит название подраздела источника; код включать, только если он есть в источнике. Для `taskbook` это точное название задачника, для `original` название задачника или подборки не заполнять: в `source.provider` указывается автор отдельной задачи. Интерфейс выбирает подпись поля по `source.kind`; слово «подборка» не используется вместо названия подраздела платформы. `source.taskNumber` — порядковый номер задачи внутри указанного контекста, `source.externalId` — внешний ID платформы или исходный номер задачи в задачнике; эти значения не подменяют друг друга.
- `type` и `grading` задают ответ по таблице ниже. `grading.policy` необязателен; отсутствие или `exact` сохраняют прежнее оценивание. Поле не добавляется автоматически при чтении старого задания. Разбор в `solution.md` необязателен; пустой файл-заглушка не создаётся.

### Предметная классификация `topicPath`

Классифицировать каждую задачу по физическому содержанию и способу решения. Учитывать условие, реально используемый рисунок, варианты утверждений и требуемый интервал времени. Название, тип ответа, номер ЕГЭ и подраздел источника сами по себе тему не определяют. Одно правило действует для автоматических и развёрнутых задач, платформ, задачников и авторских материалов.

- Выбирать наиболее конкретный обоснованный путь от общего раздела к частной теме. Первый уровень — раздел, второй — подраздел, следующие — уточнения темы. Допустимы 1–5 непустых уровней; пропущенные уровни не заполнять пустыми строками, `null`, прочерками или словом «Общее». Отсутствующие уровни в сведениях не показываются.
- Если для решения существенно несколько разных тем, остановиться на их общем родительском разделе или подразделе. Для сочетания равномерного и равноускоренного движения использовать `["Механика", "Кинематика"]`, без третьего уровня. Не придумывать тему «Смешанное движение» и не записывать несколько параллельных тем последовательными уровнями одного пути.
- Если другой режим лишь вспомогательный, а основной способ решения относится к одной теме, конкретную тему можно сохранить. Когда вопрос относится только к отдельному участку или моменту на графике, классифицировать по этому участку или моменту, а не по всем показанным режимам.
- Покой вместе с равномерным движением не считать сочетанием равномерного и равноускоренного режимов. Для общего анализа произвольного графика не утверждать постоянство ускорения, если оно не задано и не следует из графика: при отсутствии обоснованной узкой темы оставить общий путь.
- Использовать одинаковые названия для одинаковых тем во всех пакетах. Для этой кинематической иерархии приняты «Механика», «Кинематика», «Равномерное движение» и «Равноускоренное движение»; не создавать варианты названия только из-за формулировки конкретного источника.

| Содержание задачи | `topicPath` |
| --- | --- |
| Постоянная скорость, в том числе несколько равномерно движущихся тел | `["Механика", "Кинематика", "Равномерное движение"]` |
| Постоянное ненулевое ускорение, включая торможение | `["Механика", "Кинематика", "Равноускоренное движение"]` |
| Разгон и равномерный участок одинаково важны; догонка равномерно движущегося тела равноускоренно движущимся | `["Механика", "Кинематика"]` |
| Общий качественный анализ графика без обоснованного единственного режима | `["Механика", "Кинематика"]` |

Примеры проверки по содержанию: у Школково №103356 спрашивается ускорение при `t=2 с`, когда график скорости горизонтален, поэтому тема — «Равномерное движение». У №159660 весь требуемый интервал 0–6 с лежит на одном наклонном прямом участке графика скорости, а у №13395 оба графика скорости линейны с ненулевым наклоном: тема — «Равноускоренное движение». Догонки №63707 и №86767 требуют обоих законов движения и остаются на уровне «Механика → Кинематика».

`source.collection` описывает исходный каталог независимо от `topicPath`. Например, `1.06 Равноускоренное движение` сохраняется как подраздел Школково даже тогда, когда содержание конкретного вопроса требует другой или более общей предметной классификации. У задачника название, автор и исходный раздел также не заменяют самостоятельный разбор содержания.

Фильтр по родителю включает его собственные задачи и потомков. Поэтому смешанная задача с путём «Механика → Кинематика» находится по кинематике; узкий фильтр «Равноускоренное движение» её не включает. В текущем формате у задачи один путь, а не несколько тематических меток.

При исправлении только классификации сохранять стабильный `id`, исходные условия, рисунки, ответы, баллы и `source`; менять `topicPath`. Пересобрать ZIP и связанные CSV/JSON-реестры и PDF-предпросмотр, проверить их согласованность и прохождение импортера. Основания классификации хранить вне ZIP: неизвестные поля в строгий `task.json` не добавлять. Повторный импорт изменённой задачи создаёт новую версию, прежние назначения сохраняют свой снимок.

### Классификация обязательна при подготовке новых задач

Не смешивать четыре независимых признака:

| Поле | Значение и назначение |
| --- | --- |
| `type` | Как ученик отвечает: число, текст, один/несколько вариантов, соответствие или фотографии развёрнутого решения. Обязательно для каждого задания. |
| `source.exam` | `ege` — задача формата ЕГЭ; `none` — не ЕГЭ. Не выводить из темы, платформы, количества баллов или формата ответа. |
| `source.kind` | `taskbook` — задачник/сборник; `platform` — образовательная платформа; `original` — авторская задача. Источник и принадлежность ЕГЭ независимы. |
| `grading.policy` | Как начисляются баллы. Метка ЕГЭ сама не включает частичные баллы; правило выбирается явно и проверяется отдельно. |

Для `exam: "ege"` указать подтверждённые `examYear` и `examTaskNumber`; без любого из них импорт отклоняется. Это год/номер формата задания, а не утверждение, что оно было на реальном экзамене. Если задача не ЕГЭ, поставить `exam: "none"` и не передавать поля ЕГЭ. Иные экзамены этим контрактом не моделируются; не выдавать их за ЕГЭ.

Для `kind: "taskbook"` в `provider` указать автора/составителя, в обязательном `collection` — точное название задачника; издание/год можно включить в название. `externalId` — номер в исходном задачнике. Для платформы указать её название и внешний ID, если он есть. Для авторской задачи — имя автора или `provider: "Авторское"`; чужую задачу не маркировать авторской из-за отсутствия ссылки.

Примеры только объекта `source`:

```json
{"kind":"platform","provider":"Школково","externalId":"14139","exam":"ege","examYear":2026,"examTaskNumber":15}
```

```json
{"kind":"taskbook","provider":"Автор сборника","collection":"Название задачника, издание и год","externalId":"123","exam":"none"}
```

```json
{"kind":"original","provider":"Авторское","exam":"none"}
```

Второй и третий примеры иллюстрируют структуру, а не готовые задачи: реальные названия и авторов агент получает из исходника. Перед упаковкой агент должен проверить `type`, параллель, тему, максимум баллов, `source.exam`, `source.kind`, происхождение/номер и ключ/правило. Если классификация, авторство или год/номер ЕГЭ неизвестны — перечислить недостающее автору и согласовать; не подставлять текущий год и не придумывать номер. Один и тот же источник может содержать ЕГЭ и не ЕГЭ. Не путать `examTaskNumber` с `externalId` и `taskNumber`.

Для обратной совместимости сервер принимает прежние пакеты без `source.exam`/`source.kind` и не добавляет defaults. Это допуск старого формата, а не рекомендация автору пропускать классификацию. В сведениях старое задание с годом и номером ЕГЭ показывается как ЕГЭ; без полной пары и явной метки — «Не указана». Исправление классификации через импорт со стабильным ID создаёт новую версию; прежние назначения не меняются.

В банке доступны фильтры ЕГЭ/не ЕГЭ и конкретного источника. Источники группируются по точному `source.provider`: агент должен одинаково писать название одной платформы/автора во всех заданиях. `source.kind` обозначает вид происхождения и не заменяет имя provider. У задачника его название остаётся в `collection` и доступно поиску; выпадающий «Источник» выбирает provider. Непомеченные старые задачи не попадают в «Не ЕГЭ» автоматически: они остаются в общем списке до уточнения метаданных.

### Поля ответа

| type | Дополнительные поля | Закрытый grading |
| --- | --- | --- |
| `short_number` | необязательный `unit` | `answer`: десятичная строка с точкой; `absoluteTolerance`: неотрицательное конечное число |
| `short_text` | — | `acceptedAnswers`: список непустых строк; `caseSensitive`: учитывать ли регистр |
| `single_choice` | `options`: упорядоченные `{id, content}` | `correctOptionId` |
| `multiple_choice` | `options`: упорядоченные `{id, content}` | `correctOptionIds`: уникальный набор ID |
| `matching` | `rows` и `options`: упорядоченные `{id, content}` | `matches`: объект ID позиции → ID варианта |
| `extended` | только общие поля; ответ — фотографии ученика | `grading` отсутствует; решение и критерии находятся в локальном проверяющем проекте |

В `content` допускаются те же текст, математика и изображения, что в условии. Поэтому график может быть позицией А, а формула — вариантом ответа. ID позиции стабилен (`radius`, `force`, `a`, `b`), а не вычисляется из отображаемого текста. В соответствии каждый ряд получает один ответ; варианты разрешено повторять. Удалённая/лишняя позиция в ключе и несуществующий вариант не проходят схему.

`14` не является универсальным форматом ключа: это либо число, либо набор `1, 4`, либо соответствие `a → 1`, `b → 4`.

## Правила выполнения и автопроверки

Эти правила используются сервером назначенных работ и ученическим интерфейсом:

- Числовой ключ хранится без TeX, единиц, разделителей тысяч и экспоненциальной записи: `4.83`, а не `$4{,}83$`. Ввод ученика должен принимать запятую/точку и эквивалентные десятичные записи; единицы отображаются отдельно. Автоматическое преобразование единиц и проверка произвольных выражений не входят в v1.
- В образце `absoluteTolerance = 0`: точное совпадение числового значения после нормализации. Требование округления остаётся в условии; широкую погрешность агент самостоятельно не добавляет.
- Для текста: NFC и удаление краевых пробелов; регистр игнорируется только при `caseSensitive = false`. Буквы «е» и «ё» автоматически не объединяются; синонимы перечисляются в `acceptedAnswers`.
- Один вариант сравнивается по ID, несколько — как набор без учёта порядка. Соответствие сравнивается по каждой именованной позиции, а не как набор цифр.
- При отсутствии `grading.policy` или при `exact` полное совпадение даёт `maxPoints`, иначе 0. Частичные баллы включаются только явным правилом из следующего раздела; номер ЕГЭ и источник сами правило не меняют.
- Ученик получает только разрешённую публичную проекцию условия и вариантов. `grading`, `solution.md`, исходные JSON, весь ZIP и закрытые ресурсы не выдаются до отдельной публикации разбора. Приватность обеспечивает API, а не имя файла.

### Явные правила ЕГЭ: инструкция агенту

Правила основаны на системе оценивания демоверсии физики ЕГЭ-2026, печатная стр. 19 ([PDF-копия ФИПИ](https://vpr-ege.ru/z6/ege26-fi-demo.pdf#page=10)), и [официальных рекомендациях ФИПИ-2026](https://doc.fipi.ru/navigator-podgotovki/navigator-ege/MR_fizika_ege_2026.pdf), стр. 11. Это версия алгоритма `v1`, а не автоматическое обещание соответствия любому году/предмету. Для изменившихся критериев нужна отдельная согласованная версия правила; существующую `v1` менять задним числом нельзя.

| grading.policy | Допустимый type и ограничения | Начисление |
| --- | --- | --- |
| отсутствует или `exact` | любой автоматический тип, прежние ограничения | `maxPoints` за полное совпадение, иначе 0 |
| `ege_physics_matching_v1` | только `matching`, две позиции, `maxPoints: 2` | по 1 баллу за верную именованную позицию, всего 0–2 |
| `ege_physics_multiple_choice_v1` | только `multiple_choice`, в ключе 2 или 3 верных ID, `maxPoints: 2` | 2 за точный набор; 1 за одну замену, один лишний или один пропущенный вариант; иначе 0 |

Примеры закрытого `grading` (остальные поля задания остаются обычными):

```json
{"policy":"ege_physics_matching_v1","matches":{"radius":"2","force":"2"}}
```

```json
{"policy":"ege_physics_multiple_choice_v1","correctOptionIds":["1","2"]}
```

Для выбора утверждений с ключом `1,2`: наборы `1,2` и `2,1` дают 2; `1,2,3`, `1,3`, `3,1`, `1` или `2` — 1; `3,4`, `1,2,3,4`, пустой ответ — 0. Порядок кликов и порядок ID в массиве не учитываются; повторяющиеся или отсутствующие ID не принимаются. Технически число ошибок — максимум из количества пропущенных и лишних ID: замена одного варианта считается одной ошибкой, а не двумя.

У соответствия позиции А/Б не переставляются: проверяется `matches[row.id]`, а не набор выбранных цифр. В структурированном вводе приложения пустая позиция считается ошибочной: одна верная и одна пустая дают 1; обе пустые — 0. Это явная адаптация к двум отдельным полям сайта; правила заполнения бумажного бланка и лишние символы в них не моделируются. Использование одного варианта в двух позициях допускается, если оно согласуется с ключом.

Не назначать правило ЕГЭ обычному двухбалльному заданию только из-за `maxPoints: 2`. Не переносить эти правила на `short_number`, `short_text`, `single_choice`, `extended` или задания ЕГЭ с другой шкалой. Несовместимый тип, неизвестный policy, неверное число позиций/ключей или максимум отклоняются схемой. `extended` по-прежнему не содержит `grading`.

Изменение policy — изменение содержания проверки: сохранить stable ID и передать исправленный `task.json`. Импорт создаст новую версию, старые снимки назначенных работ и сохранённые результаты останутся прежними. Даже незавершённая ранее назначенная работа продолжает проверяться по своему снимку. Для новой шкалы нужно собрать/назначить работу с новой версией задачи. Не редактировать опубликованные JSON/БД и не запускать пересчёт старых попыток.

Готовый пример: `examples/assessment-package/ege-v1/` содержит те же задачи `shkolkovo-14139` и `shkolkovo-17846`, что пилот, с явными policy. Условия, ключи, баллы и источники сохранены. Его импорт в банк с пилотом обновит именно эти две записи новыми версиями; без явного импорта ничего не меняется. Предварительно показать изменения преподавателю.

Сборка примера без TeX (из `examples/assessment-package/ege-v1/`):

```bash
zip -qr ../../../output/assessment-package-ege-v1.zip manifest.json tasks
unzip -t ../../../output/assessment-package-ege-v1.zip
```

После импорта раскрыть «Источник и сведения»: проверить «Тип задания» и «Правило оценивания». В «Просмотре работы» проверить минимум три случая через сервер: полный балл, 1 из 2 и ноль. Пробная проверка не сохраняет ответы и не меняет статистику; окончательное выполнение ученика использует тот же оценщик. Цвет числового результата: зелёный для полного балла, янтарный для промежуточного, красный для нуля; словесной оценки рядом нет.

## Markdown и рисунки

UTF-8, обычные абзацы и списки, таблицы GFM, формулы `$...$` / `$$...$$`. Изображение задаётся Markdown-конструкцией с описанием и относительным путём, например `images/flux-time.jpg`; разрешены только локальные `images/<имя>.png|jpg|jpeg|webp` с латинскими именами. Синтаксис виден в `statement.md` задания `shkolkovo-65365`. Условия, варианты и позиции используют одинаковые правила. Существование ссылок и файлов проверяет импортёр. Обычные ссылки допускаются только через HTTPS; HTML и блоки кода отклоняются. Глубина Markdown ограничена 20 уровнями, фрагмент — 120 000 символами, формула — 4000 символами.

Для единообразной типографики сохранять математическое выражение целиком внутри одной пары разделителей: `$B = 1$`, а не разносить переменную, знак и значение между TeX и обычным текстом. В TeX десятичную запятую записывать как `4{,}8`, не меняя запятые обычного текста. Короткие выражения оставлять строчными; отдельные формулы — самостоятельными блоками `$$...$$`. Не вставлять пробелы, пустые абзацы и принудительные переносы ради подгонки экрана. Единицы и содержание сохранять по источнику; не переписывать уже назначенные версии ради внешнего вида. Общий renderer отвечает за метрики формул, интервалы, выравнивание и адаптацию, а не CSS отдельных заданий.

В общем MathJax запрещён браузерный разрыв inline-выражения на части (`output.linebreaks.inline = false`): короткое равенство переносится целиком. Слишком широкое содержимое прокручивается внутри Markdown-блока, а не расширяет страницу. Длинные самостоятельные выводы следует готовить блоками `$$...$$`.

Не переносить HTML, JavaScript, CSS, внешние картинки, пути `..`, абсолютные пути, `\input`, преамбулу, `\newpage` и `minipage`. Вёрсткой экрана управляет приложение. MathJax предназначен для математики, а не исполнения полной LaTeX-программы; загрузка расширений, макросы и HTML-команды в формулах отклоняются. TeX вне формул не исполняется и не заменяет Markdown. Ширину и мобильную раскладку рисунков нужно проверять в интерфейсе банка; PDF-предпросмотр этого не подтверждает.

Необходимые константы из общего `reference-data.tex` должны остаться доступны при отдельной выдаче задачи. В пилоте постоянная Больцмана явно добавлена к условию №11121 из исходного справочника. Не добавлять формулу решения под видом справочных данных.

### Обязательная подготовка формул

После Pandoc или другого конвертера проверить фактический Markdown. Конвертация без ошибки и корректный PDF не подтверждают работу экранного renderer.

- Внутри предложения использовать одну пару `$…$`, без переноса строки внутри: `Координата изменяется по закону $x = 18 + 32t - 6t^2$.`
- Самостоятельную формулу помещать отдельным блоком: пустая строка перед и после, открывающие и закрывающие `$$` на отдельных строках. Это структурные границы Markdown, а не подгонка отступов экрана.
- Не генерировать `$$…$$` посреди предложения. Parser поддерживает такие сохранённые условия для совместимости; новые архивы должны иметь однозначную структуру.
- Проверять пары и длину разделителей. Не смешивать `$` и `$$`, не оставлять одиночные/тройные `$`. Обычный знак доллара в тексте записывать как `\$`.
- Русские пояснения «где», «выражено в секундах», «Определите…» оставлять обычным текстом за закрывающим разделителем. Не допускать захвата остатка предложения в математический узел.

Корректный самостоятельный блок:

```markdown
Координата тела $x$ изменяется с течением времени $t$ согласно закону

$$
x = 18 + 32t - 6t^2,
$$

где $t$ выражено в секундах, а $x$ — в метрах.
```

### Проверка готового ZIP перед передачей

При конвертации из TeX использовать Pandoc writer `markdown-smart+tex_math_dollars` (smart отключён у writer). Обычный `markdown` с включённым smart может записывать готовое длинное тире как `---`; наш CommonMark renderer исторически показывал три дефиса буквально. В новых архивах обычное тире должно быть Unicode `—`, диапазон — `–`, кавычки — типографическими символами по контексту. Проверять результат конвертации, а не заменять дефисы во всём файле: минусы внутри формул, ID/имена файлов, Markdown-таблицы и горизонтальные разделители имеют другую семантику. Общий parser исправляет отдельное `---` в обычном тексте сохранённых заданий для совместимости; это не разрешение оставлять такой артефакт в новом ZIP. Проверка исходных фрагментов должна выявлять его до передачи.

Агент выполняет все уровни проверки; непроверенное явно перечисляет в отчёте:

1. Прочитать именно финальный ZIP действующим `parseAssessmentArchive`. Проверить схему, стабильные ID, ключи, файлы и рисунки. Проверять `statement.md`, `solution.md`, каждый `options[].content` и `rows[].content`. Ошибка должна указывать задачу и файл/поле. `unzip -t` проверяет целостность ZIP, но не содержание задачи.
2. Независимо выписать из исходных Markdown все формулы с точным TeX и признаком inline/display. Сравнить полный упорядоченный список с математическими узлами `parseAssessmentMarkdown`. Одного числа формул или успешного вызова parser недостаточно. Пропущенная формула либо русский текст вместо исходного выражения блокируют передачу.
3. Пропустить каждую сверенную формулу через текущий MathJax; проверить отсутствие `merror`/`data-mjx-error`. Нулевое число ошибок MathJax само по себе недостаточно: потерянную формулу он не проверит, а ошибочно захваченный русский текст может считать допустимой математикой.
4. Проверить все задачи общим экранным компонентом `AssessmentMarkdown` после завершения MathJax и загрузки шрифтов: desktop и узкий экран 375–390 px, условие, варианты/позиции и рисунки. Проверить фактическую загрузку и размеры рисунков, индексы/дроби и соседний обычный текст. Страница не должна расширяться за viewport; локальная прокрутка широкой формулы/таблицы допустима. PDF проверять отдельно: у него другой тракт отображения.
5. После последней правки заново собрать и проверить ZIP, сверить с PDF/реестром и записать SHA-256 доставляемого файла. Не относить старый результат проверки к пересобранному архиву. В отчёте разделять структуру ZIP, MathJax, экранный просмотр и настоящий импорт/проверку в авторизованном приложении.

Регрессионный пример — Школково №16656. В исходном условии семь формул: `x`, `t`, `x = 18 + 32t - 6t^2,`, `t`, `x`, `a_x`, `^2`. Раньше `$$…$$` внутри абзаца терялось в блоковом tokenizer, а следующие `$` захватывали русский текст. ZIP и PDF проходили проверки. Поэтому проверки только уже извлечённых MathJax-фрагментов недостаточно.

### Точечное исправление уже выданной задачи

Использовать «Банк заданий → Действия с заданием → Исправить условие». «Скачать эту задачу» выдаёт ZIP ровно с одной задачей. Его можно передать агенту, исправить локально и вернуть в диалог. Обычный импорт пакета не обновляет назначенные снимки автоматически.

В исправляющем ZIP:

- Оставить единственный прежний ID в `manifest.tasks`, папке и `task.json.id`. Не выдавать новую задачу за исправление прежней.
- Скопировать `task.json` из скачанного ZIP без изменения названия, типа, параллели, `topicPath`, `source`, единиц, `maxPoints`, `grading`/policy, ID и порядка вариантов/позиций. Разрешено исправлять только их `content`, сохраняя смысл и соответствие прежним ключам.
- Исправлять `statement.md`, оформление `solution.md` и используемые рисунки. Для повреждённого/забытого рисунка передать корректный локальный файл с согласованной Markdown-ссылкой. Удалить неиспользуемые файлы. Повторить все проверки готового ZIP.
- Не менять числовые данные, физический смысл или правильный ответ под видом вёрстки. Совпадение ключа не доказывает неизменность смысла; её проверяет преподаватель по сравнению «Сейчас / Исправление».

Преподаватель подтверждает «Смысл задачи и правильный ответ не изменились» и нажимает «Сохранить в банке и работах». Создаётся новая версия отображения; совместимые условия в черновиках, назначенных, начатых и завершённых работах читаются с исправлением. Ответы, баллы, фотографии, порядок и статус не сбрасываются и не пересчитываются. К старой версии с другим ключом/структурой исправление не применяется. Открытая ученическая вкладка получает его через существующую проверку доступности (обычно до 10 секунд при видимой вкладке), введённый ответ сохраняется.

При ошибке ключа, шкалы или смысла нужен другой сценарий: обычное обновление банка и отдельное решение преподавателя о назначениях/оценивании. Режим исправления такие изменения отклоняет. Отмена оформления — загрузка прежнего содержания как нового исправления; история версий сохраняется.

Сборка отдельного образца: из `examples/assessment-package/extended-v1/` выполнить `zip -qr ../../../output/assessment-package-extended-v1.zip manifest.json tasks`, затем проверить `unzip -t ../../../output/assessment-package-extended-v1.zip`. Этот ZIP загружается обычным учительским импортом; серверный TeX не нужен.

Проверка и воспроизводимая сборка (локальные Node.js, Pandoc, XeLaTeX, Arial и zip):

```bash
pnpm --filter @continuum/shared test
pnpm --filter @continuum/shared build
node scripts/assessments/build-pilot-preview.mjs
unzip -t output/assessment-package-pilot-v1.zip
```

Результат: `output/assessment-package-pilot-v1.zip` и `output/pdf/assessment-package-pilot-v1.pdf`. PDF содержит ключи на последней странице и предназначен преподавателю. Скрипт собирает только этот образец, не является валидатором произвольного ZIP или серверным импортером; локальный TeX не добавляется в production runtime.
